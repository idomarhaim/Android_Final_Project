## 1 · `screenrecord` silently downgrades to 720×1280, exits 0, and nothing downstream says so

**Claim.** `adb shell screenrecord` at a modern AVD's native resolution fails to configure the AVC
encoder, **prints a warning, falls back to 720×1280, records anyway, and exits 0.** The failure is
therefore invisible to every check that is not reading `screenrecord`'s own stderr — the file
exists, the duration is right, the beat map is right, and the pixels are a quarter of what was
asked for.

`Observed:` 2026-08-24, `emulator-5554` (1344 × 2992, Android 15):

```
ERROR: unable to configure video/avc codec at 1344x2992 (err=-22)
WARNING: failed at 1344x2992, retrying at 720x1280
```

The first take of this session ran **two and a half minutes** at 720p before the log was read.

**The ceiling is measurable and is not the native size.** Binary search against the same encoder,
same session:

| size | result |
|---|---|
| 1344 × 2992 (native) | ERROR |
| 1280 × 2848 | ERROR |
| 1216 × 2704 | ERROR |
| **1152 × 2560** | **OK — the ceiling** |
| 1080 × 2400 | OK (what the 2026-08-22 cut used) |

**Why it matters beyond this repo.** The remedy is not *"pass `--size`"* on its own — a wrong
`--size` downgrades just as silently. It is **pass `--size` and then read the tool's own stderr and
refuse to continue**, which is `kb/dev/look-at-your-own-output.md` applied to a tool that reports
success while doing something else. The generalisable shape: *a tool that degrades gracefully is a
tool that hides its degradation from your exit-code check.*

**Rejected:** trusting the native screen size (that is what failed); probing the finished file's
resolution afterwards (correct, but it costs a whole take to learn); hard-coding 1080 × 2400 from
the previous session (works, and throws away 42 % of the pixels this encoder will actually give).

- **Destination.** `kb/dev/android-device-verification.md` — §6.2 already covers recording a motion
  feature and names the 720×1280 fallback in passing; this promotes it from an aside to a measured
  procedure with a ceiling-finding method and a guard.
- **Anchors.** `scripts/record-tour.sh` trap 5 and `start_recording`; `CHANGELOG/2026-08-24/62-tour-video-v2.md`.
- **Supersedes.** Nothing. It **sharpens** the existing §6.2 sentence, which says the fallback
  happens but not that it exits 0, and gives it a number.
- **Status.** ready.

## 2 · A substring match over a UI hierarchy needs a positional band, or it taps the wrong node

**Claim.** Locating a control by `text=` substring across a whole `uiautomator` dump takes the
**first** match in document order, and screen words are not unique. A bottom-bar tab label
routinely also appears in content further up the same screen, so the tap lands somewhere plausible
and the run continues on the wrong screen.

`Observed:` 2026-08-24. A rehearsal tapped `Goals` and hit the friends feed's *"avg 24% across 7
goals"* at **y = 1735** instead of the tab at **y = 2848**. Nothing failed: the tap registered, the
next `uiautomator` dump succeeded, and **every one of the following seven acts ran against the
wrong screen** and logged 18 misses that all read as *"the label must have changed"*.

**The remedy is one line and it is not "match exactly".** Exact matching breaks the moment a
designer adds a word, which is why substring matching was chosen. Bound the search by **where** the
thing is instead: a tab lives in the bottom 12 % of the screen, so `tap_tab` filters candidate
nodes by their y-centre before taking the first. Same substring, same tolerance to copy changes,
no ambiguity.

**Why it is worth a page.** It fails in the direction that looks like a *content* problem — the
symptom is a stream of "MISS text=…" on later screens, which sends you to check strings that are
perfectly correct. The cause is one tap, twenty steps earlier.

- **Destination.** `kb/dev/android-device-verification.md`, alongside the existing
  `uiautomator`-measurement material.
- **Anchors.** `scripts/record-tour.sh` — `node_center`'s band parameters and `tap_tab`.
- **Supersedes.** Nothing.
- **Status.** ready.

## 3 · Git Bash rewrites a *device* path, so `adb shell` writes somewhere you did not ask for

**Claim.** MSYS path conversion applies to arguments that look like absolute POSIX paths **even
when the path belongs to the device, not the host**. `adb shell uiautomator dump /sdcard/ui.xml`
becomes a dump to `/Files/Git/sdcard/ui.xml`, and a subsequent read of `/sdcard/ui.xml` returns a
**stale** file from an earlier run.

`Observed:` 2026-08-24 — the tool reported `UI hierchary dumped to: /Files/Git/sdcard/ui.xml` while
the pull happily returned 10 055 bytes of an older hierarchy.

**Why it is dangerous rather than annoying.** A stale hierarchy is indistinguishable from *a screen
that did not change*, which is precisely the conclusion a UI-driving script is trying to reach. It
fails toward "the tap did nothing", so the instinctive fix is to tap again.

**Remedy.** `MSYS_NO_PATHCONV=1` on every `adb shell` / `adb exec-out` invocation, applied once in
a wrapper rather than at each call site; quoting the whole remote command also works.

- **Destination.** `kb/dev/android-device-verification.md`, and cross-linked from the project's
  `CLAUDE.md` Windows-traps list, which already carries the `local.properties` backslash trap and
  the `${PIPESTATUS[0]}` trap. This is the same family: *the shell treats your data as syntax.*
- **Anchors.** `scripts/record-tour.sh` — trap 3, `sh_()` and `out_()`.
- **Supersedes.** Nothing.
- **Status.** ready.

## 4 · A build minutes old can be the shipped app on every screen but one, and nothing on screen says which

**Claim.** *"The emulator has the current build"* is a claim about **file times**, not about what is
on screen, and it cannot be checked by looking. Verify it by asserting that **no source file is
newer than the built APK**, mechanically, before a take.

`Observed:` 2026-08-24. The emulator carried a debug APK built at **01:56**. `DashboardScreen.kt`
and `DashboardViewModel.kt` were last written at **02:01:43** and committed at 02:13. So the
installed app was the shipped commit in every visible respect **except the screen the tour opens
on** — and this app never renders `BuildConfig.VERSION_NAME` anywhere, so no frame of the recording
would have said so. The APK's own `versionName` read `0.3.3-debug` while its code was `9af6424`,
because the version bump landed after the build.

**The generalisable half.** A version string identifies *a release decision*, not *a build*. Where
the two are set in different commits — which is normal, since the bump is usually the last edit —
the version string is evidence about neither. The file-time comparison is evidence about both.

- **Destination.** `kb/dev/android-device-verification.md`, as the precondition every
  device-verification recipe there already implicitly assumes.
- **Anchors.** `scripts/record-tour.sh` — `assert_build_is_current`.
- **Supersedes.** Nothing.
- **Status.** ready.

## 5 · Rehearse a UI script with writes disabled — it is the only cheap way to find selector rot

**Claim.** A device-driving script has two independent failure surfaces: **navigation** (does the
run reach the screen) and **mutation** (does it type, create and move the right things). They can
be tested separately, and only the first is cheap to repeat. So give such a script a
`--no-writes` mode that walks every screen, resolves every selector and **skips the three or four
steps that change real data** — then run it twice before a take.

`Observed:` 2026-08-24. Two rehearsals cost about twenty minutes of machine time between them and
found: a missing return-to-root after the goal-detail act (which broke seven acts), four wrong
`content-desc` values, an analytics period with no data behind it, a section header that becomes
visible while all four of its cards are still below the fold, and the ambiguous-tab-label defect
in entry 2. **None of those would have failed loudly during a take** — they would have produced a
finished video with nine minutes of the wrong screens in it.

**Why the write/no-write split is the right seam**, rather than a general dry-run flag: it is the
one seam where *repeatability* changes. Navigation is idempotent and can be run twenty times;
creating a task and dragging a real calendar block is not, and a rehearsal that leaves two junk
tasks behind buys itself a cleanup pass — and a cleanup pass is a deletion, which is always-ask.

- **Destination.** `kb/dev/android-device-verification.md`, as a method rather than an incident.
- **Anchors.** `scripts/record-tour.sh` — `writes_ok`, `--no-writes`, `--dry-run`.
- **Supersedes.** Nothing.
- **Status.** ready.

## 6 · A marketing film of an app is a film of its **data**, and the account can be empty of exactly the new features

**Claim.** When a tour exists to show what shipped since the last tour, check the **account** for
the data each new feature needs *before* planning the shot list. A feature can be complete,
correct, fully tested and green, and still render an empty state on the only account you can film.

`Observed:` 2026-08-24, Ido's live account, five of the tour's beats:

| beat | what the screen actually said |
|---|---|
| Overall progress | *"No goal has a number yet"* — **no** goal on the account has a measure |
| `#64`'s kept / missed / still-owed run | *"Nothing has been due here yet"* on **every** life area |
| The calendar (`#60`) | one entry; the day reads *free* |
| The scope sheet (`#68`) | needs a **recurring** block, and there is none |
| Analytics, week and month | empty — **only** the Year view has data |

`#64` and `#65`/`#66` are the two the brief singles out as *"the beats that say something about
the product rather than about a feature"*, and one of them has nothing to draw.

**Why this is not a bug report.** Nothing is broken. The finding is about **sequencing**: a data
audit is a five-minute `uiautomator` pass and it belongs *before* the choreography is written, not
after a take is in the can. The failure it prevents is expensive and silent — a finished film whose
strongest feature is on screen as an empty state.

- **Destination.** A new page. Nearest existing home is `kb/dev/android-device-verification.md`,
  but this is not device verification — it is *demo-data readiness*, and it generalises to
  screenshots, store listings and examiner demos as readily as to video.
- **Anchors.** `docs/marketing/explainer-video-brief.md` §7's third table, added this session.
- **Supersedes.** Nothing.
- **Status.** ready.
