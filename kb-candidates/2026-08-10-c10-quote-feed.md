## 1. Split a feature at the thing it must not get wrong, not at what it does

**Claim.** When one requirement bundles two obligations and only one of them is
*unforgivable* if broken, the seam goes at the unforgivable one — not at the functional
boundary that looks natural. Every other split is an optimisation; this one is a
guarantee, because after it the forbidden outcome is **unreachable by construction**
rather than prevented by care.

**Why.** The concrete case: a product requirement asked for a daily sentence that was
both *"practical and inspiring"* and *"drawn from a bestselling book or a famous figure"*.
The natural reading is one feature with two adjectives, and every design for it either
produced platitudes (nothing specific to say) or invited an LLM to attribute words to a
real person — which is the app lying about a human being, and was a hard constraint, not
a quality bar. Splitting on **attribution** — a curated store is the only thing allowed to
name a human; the generative half names nobody — makes both halves easy: the corpus needs
no cleverness, and the model needs no truthfulness about the world, only about the user's
own data. Rejected alternative: one generative feature with a strong prompt telling the
model to only quote real sources. That is prevention-by-instruction, and it fails
silently — a fabricated attribution is indistinguishable from a real one at read time.

**Generalisation beyond quotes.** The same seam appears wherever a generated artifact must
carry a verifiable external reference: citations in a summary, a price quoted from a
catalogue, a legal clause, a medical dosage. The reference comes from a store; the prose
comes from the model; the model never authors the reference.

**Destination.** `kb/dev/` — likely a new page on partitioning AI features by
inviolable constraint. Check for overlap with `dev/llm-structured-output.md`, which is
about format reliability rather than about where a feature's seam belongs.

[#29](https://github.com/idomarhaim/Android_Final_Project/issues/29) §"The three
sub-questions" · `CHANGELOG/2026-08-10/c10-quote-feed.md` §"The decision".

## 2. Prefer making a failure unreachable over checking for it

**Claim.** When a component has a **measured** failure mode on a particular kind of input,
the strongest fix is not a validator on the way back — it is a design where that input is
never handed to it. A check is a control that can be forgotten, mis-scoped, or removed by
someone who does not know why it is there; an input the component never receives cannot be
corrupted at all.

**Why.** A prior session measured this project's free LLM at 248 live calls and found
exactly one failure mode: **free identifiers come back silently corrupted** — a
20-character id returned as 18 characters, plausible, correctly typed, and catchable only
by membership in the list that was sent. The standard remedy is a membership check, and
this repo already applies one. The stronger remedy, available here, was to restructure the
call: the model returns a value from a **prompt-declared enum** (measured perfect in the
same run) and the app resolves that enum to the identifier locally. The id never crosses
the wire in either direction, so there is nothing to check. Note the asymmetry that makes
this cheap: the enum is a small closed vocabulary the app already owns, so the model's job
got *easier*, not harder.

**The tell for when this applies:** you are about to write a validator whose failure branch
is "fall back to what we would have done anyway". If the fallback is that cheap, the model
was not adding information at that step, and the step can usually be moved.

**Destination.** `kb/dev/` — update **in place** on `dev/llm-structured-output.md`, which
already carries the id-corruption finding and the membership-check remedy. This is the
next paragraph of that page, not a new one.

**Anchors.** `docs/research/2026-08-08-free-model-format-probe.md` (the measurement) ·
resolution comment on [#29](https://github.com/idomarhaim/Android_Final_Project/issues/29)
§2 (the restructure).

**Supersedes.** Nothing — it extends the existing page rather than contradicting it. The

## 3. Choose between designs by their degraded mode, not their happy path

**Claim.** When two designs are close on the happy path, the tiebreaker that predicts
real-world quality is what each becomes when its expensive dependency is unavailable.
A design whose fallback is **the same feature with one input substituted** is categorically
better than one whose fallback is **a different mechanism** — even when the second is
better while everything works.

**Why.** Two selection designs were compared for the same feature. In (a) the model
returns a category and the local code resolves it; with no network the code derives the
category itself and *the entire rest of the pipeline is identical* — same data, same
filter, same output, and the user cannot tell from the screen that anything failed. In (b)
the local code narrows the candidates and the model chooses among them; with no network
there is no choosing step at all, so the fallback is an arbitrary pick — a **substitute
feature** wearing the same UI. (b) is genuinely better online, and it was rejected anyway.

The deeper reason: a fallback that is a different mechanism is a **second implementation**,
and second implementations get less testing, drift from the first, and are exercised
precisely when nobody is watching. A fallback that is one substituted input shares all its
code with the primary path, so it is tested every time the primary path is.

Rejected framing: "just pick the better one and accept a weaker fallback." That treats the
degraded mode as rare. On a permanently-free-tier product with rate ceilings, the degraded
mode is not rare — it is a normal operating state.

**Destination.** `kb/dev/` — new page, or a section on an existing resilience/fallback
page. Check `dev/recovery-masks-failure.md`, which is about a *neighbouring* trap (a
recovery path so good it hides that the failure is recurring) — related enough to
cross-link, different enough not to merge.

**Anchors.** `CHANGELOG/2026-08-10/c10-quote-feed.md` §"The argument that actually decided
it was the fallback, not the safety" · resolution comment on

## 4. "I don't understand the options" means the axis is not reduced far enough — corroboration, not a new claim

**Claim.** When a user answers a multi-option question with *"I could not understand you or
what each option implies"*, the productive response is **not** more explanation inside the
options — it is reducing the question to a smaller axis and re-asking. In this session the
fix that worked, twice, was collapsing four prose-heavy options into a **2×2 of who does
which job**, stated before the picker rather than inside it.

**Why.** Two consecutive question pickers came back with the identical complaint. Both were
dense: multi-sentence option bodies, reasoning nested inside each choice, and vocabulary
inherited from the tickets. The recovery that worked was to name the two sub-jobs the
question was really about ("deciding *what kind* of thing, and deciding *which* one"),
observe that each could be done by either party, and present the same four options as a
2×2 table. The options did not change; only their presentation did — which is the evidence
that the problem was framing, not content. Every subsequent picker was short and was
answered directly on the first attempt.

**Why this is filed as corroboration.** A parked candidate from the `entity-model-intake`
session, written a day earlier and still awaiting Ido, states a stronger and more general
version: *"'It doesn't understand me' usually means every option shares a framing the user
doesn't hold."* This session hit the same wall independently, from a different task, and
the recovery was consistent with that diagnosis — the shared framing here was *"selection
is one decision"*, and the 2×2 broke it into two. **Two independent sessions reaching the
same finding is the strongest argument for that entry**, so this should be ingested **into**
it rather than beside it.

**Destination.** Wherever the `entity-model-intake` parked entry lands. ⚠️ **Note the
tension the other entry already flagged:** this is arguably a `rules/` change (how the
agent should ask), which is **always-ask** and owned by the walkthrough rule, not by
`/kb-ingest`. Filed here so it is not lost; not filed as a KB page in its own right.

**Anchors.** `kb-candidates/2026-08-09-entity-model-intake.md` entry 1 (the parked, more
general claim) · `CHANGELOG/2026-08-10/c10-quote-feed.md` §"Ido asked twice for the same
thing".

## 5. A translation carries its own copyright — the original being public domain says nothing about it

**Claim.** When sourcing text in more than one language, the licence must be checked **per edition, not per work**. A translation is a **derivative work with its own copyright and its own term**, so a public-domain original does not yield a freely usable translation. Marcus Aurelius is free; a 2010 Hebrew edition of Marcus Aurelius is not.

**Why.** This was written into a committed design decision as a *reason to prefer* the public-domain route — *"those works often already have published Hebrew translations, so the second language is sourced rather than invented"* — and it is simply false. It survived a seven-question grilling and an explicit confirmation gate, because the error was inside an option rather than between options. The practical consequences are sharp and worth carrying with the claim:

- **Natively-source-language material is disproportionately valuable** in a bilingual product, because it has no translation in its licence path at all. For a Hebrew product that means Pirkei Avot and Tanakh are not merely thematically apt, they are the only part of the classical pool that is unambiguously free in Hebrew.
- **Sizing is per-language, not global.** The smaller-language pool sets the repeat interval, so a corpus is built from the constrained language outward, not assembled in English and translated afterwards.
- Rejected alternative: machine-translate the originals. That fails a *different* constraint — an attributed quote that has been paraphrased is no longer the quote, and attributing a paraphrase to a named human is the same misattribution in a smaller coat.

**Destination.** `kb/` — a reference-grade licensing fact rather than a dev practice. Likely `kb/dev/` alongside content-sourcing guidance, or a `reference/` page if the bundle has one. Small, standalone, and cheap to check against.

**Anchors.** Correction comment on [#29](https://github.com/idomarhaim/Android_Final_Project/issues/29#issuecomment-5242005728) §A1 · `CHANGELOG/2026-08-10/c10-quote-feed.md` §"The correction pass".

## 6. A confirmation gate tests whether the user understood you, not whether you were right

**Claim.** Structured elicitation — one question at a time, options on a single named axis, a final "accept or change something" gate — is adversarial about **which option to choose** and entirely trusting about **the facts inside each option**. So it converges on a decision the user genuinely endorses while carrying forward every factual error the proposer made. The remedy is a **separate pass that reviews the delivered answer as an artifact**, after it is written, asking only *what here is wrong* — not *which option is best*.

**Why.** Measured, on one session: seven grilling questions, plain-language re-explanations, a schematic summary, and an explicit accept-or-change gate produced a resolution that was then committed and indexed. A single follow-up question — *"is there anything you can improve in the solutions you chose?"* — produced **nine findings, three of them wrong answers rather than missing ones**, including a licensing error, a spec that contradicted its own stated rationale, and an unread dependency on another ticket that had explicitly named this one.

Note *where* the three errors sat: all inside options, none between them. The gate asked "is this the right choice among these?", and every option had already been accepted as internally accurate by the time it was rendered. That is a structural blind spot in the method, not a lapse in a particular run — which is why the fix is a second pass rather than more care in the first.

**Cheapest form of the remedy:** before the commit gate, re-read the artifact and ask three questions of it — *which factual claim here did I not verify · which of my own arguments does my spec contradict · which open ticket names this one*. All three of that session's errors are caught by exactly one of those.

**Destination.** `kb/dev/` — near the decision-elicitation material. Check for overlap with `dev/decision-map-charting.md` (which is about charting decisions, not about verifying a delivered one) and with the parked `entity-model-intake` entry that candidate 4 corroborates — related, but that one is about the *question* being unaskable, and this one is about the *answer* being unverified.

**Anchors.** `CHANGELOG/2026-08-10/c10-quote-feed.md` §"The correction pass — and what it says about the grilling that preceded it" · the two comments on [#29](https://github.com/idomarhaim/Android_Final_Project/issues/29), which are the before and after.
