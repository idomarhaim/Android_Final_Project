## 1 — An expiring guard test **closed the loop across three sessions**, and this is the run that proves it

**Claim.** A guard test that is *red while a premise holds* and *`skipped` the moment it flips* is
a working mechanism for handing a deletion authorisation between sessions that never meet. It
carries a fact no ticket can carry — the state of `HEAD` at the moment of execution — and it does
so in a form a downstream session can read **mechanically**, with no judgement and no prose.
`Observed:` end to end, 2026-08-20.

**Why.** The three-session loop ran in full and each half did its job:

1. `50b-transaction-guard` (2026-08-20) wrote `app/src/test/.../guards/OfflineWriteGuardTest.kt`
   *because* #50 §5's premise (*"`C20` removes the transaction"*) had been false for six days and
   nothing downstream would have caught it.
2. `c20-build-half` (`731961b`, `e5e0ef0`) made `setDone` one `update()`. The guard went from
   **green to `<skipped/>`** on its own, with that session neither editing nor consulting it — and
   deliberately did **not** perform the deletion it had just authorised.
3. `50-finish` (this session) ran the guard as its **first** action, read `skipped="1"` out of the
   JUnit XML, and only then deleted. The authorisation came from the code, not from the ticket.

The generalisation: where a ticket authorises a **deletion** on a stated premise, the always-ask
human gate has already been spent, so the premise must be re-checked by something that cannot be
skimmed. A guard test is that something, and its **skip** — not its pass — is the go signal.
`Inferred:` this generalises past deletions to any ticket-granted irreversible action whose
stated premise is a checkable property of `HEAD`.

**Rejected:** *"the ticket said so, so execute"* — that is exactly the failure the guard exists to
prevent, and it is candidate 3 of `2026-08-19-50-offline-stamps.md` seen from the other end.
Also rejected: letting the C20 session perform its own authorised deletion, which would have made
one build both grant and spend the authorisation.

## 2 — The console summary is not merely ambiguous between skip and pass; it says **nothing at all**

**Claim.** For a single-test Gradle run, `:app:testDebugUnitTest` prints no per-test line at all —
only `BUILD SUCCESSFUL`. So a guard that signals by **skipping** cannot be read from the console
in the weaker sense either: there is no ambiguous line to misread, there is no line. The JUnit XML
(`app/build/test-results/testDebugUnitTest/TEST-*.xml`, attribute `skipped="N"` / element
`<skipped/>`) is the only surface that carries it.

**Why.** `Observed:` 2026-08-20. `sessions/50-finish.md` warned *"a skip and a pass look alike
there"*; the actual run was **stronger** than the warning — 25 lines of task status, `BUILD
SUCCESSFUL in 7s`, and zero mention of the test. An agent that trusted the console would have read
a green build as a green guard and deleted on a premise it never checked. This is the
*look-at-your-own-output* duty in its exact intended shape: the consumer that decides (the XML
parser) is not the surface that reports (the console).

**Rejected:** adding `--info` or a test logger to make the console honest — it makes *this* run
readable and leaves every other session reading the same misleading default. The XML is already
authoritative and already written on every run.
