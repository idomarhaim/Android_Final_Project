## 1. `\\` in a double-quoted Bash-tool string eats the backslash AND the variable

**Claim.** In the Claude Code **Bash tool** on Windows, a `\\` written inside a double-quoted string
reaches `bash` as a **single** `\`, which then escapes the following `$`. So

```bash
V=hello
echo "dir\\$V"      # -> dir$V
```

The backslash **disappears** and the variable is **not expanded**. `od -c` on that argument gives
exactly `. p r o b e $ V` — eight bytes, no separator, no substitution. A forward slash behaves
normally: `"dir/$V"` gives `dir/hello`.

**Why this is dangerous rather than merely annoying.** The mangled argument is still a *perfectly
legal filename*, so whatever consumes it **succeeds**:

```
adb pull <remote> ".probe\\$NAME"
  -> 1 file pulled, 0 skipped. 0.7 MB/s (33401 bytes in 0.048s)
```

…and what it created is a **file called `.probe$NAME`** in the working directory — right content,
right byte count, wrong place, and a truthful success message. `ls .probe/` is empty. Run in a loop
over three files, all three land on the **same** name and overwrite each other, so three reported
successes leave one file. `Observed:` 2026-08-23, GoalPilot `#68`, pulling render-pass PNGs off
`emulator-5554`; reproduced deliberately afterwards with the `echo`/`od` above, and the stray
artifacts (`.shots68$f`, `shots$f`, `.probe$NAME`) are what the mechanism leaves behind.

**It defeats the render-pass duty specifically.** A session that pulls a screenshot this way and
then reasons about it is reasoning about a file it does not have, and
`kb/dev/look-at-your-own-output.md`'s check is satisfied *on paper* — a byte count was printed.
This is that page's own thesis in a new place: the instrument degrades silently on exactly the case
it exists for.

**Two remedies, and the first is the one to reach for.**

1. **Use the PowerShell tool for any command taking a Windows-form path argument.** It worked first
   time, with no escaping at all. This is the honest split: the Bash tool is for POSIX work, and a
   `C:\...` argument is not POSIX work.
2. If it must be Bash: **build the path with forward slashes** (`"$DIR/$NAME"`) and let the Windows
   binary normalise them, which `adb` does.

**Why (what was rejected).** *"Use `MSYS_NO_PATHCONV=1`"* — a different problem, and setting it is
what got far enough to hit this one. Without it MSYS rewrites the **remote** argument too and `adb`
errors honestly (`failed to stat remote object 'C:/Program Files/Git/sdcard/...'`); with it and a
POSIX destination it also errors honestly (`cannot create file/directory '/c/Users/...'`). **Both
of those are safe failures.** Only the Windows-form destination is silent, which is the ordering
that makes this worth writing down: the two spellings that look wrong fail loudly, and the one that
looks right fails quietly.

`Untested:` whether the same collapse happens outside double quotes, in single quotes, or in a
heredoc body. Every instance observed was a double-quoted argument.

- **Destination:** `kb/dev/` — this is a **harness** finding, not an Android one, so it belongs
  wherever the Bash/PowerShell tool traps live (`kb/dev/powershell-encoding-traps.md` has the
  nearest subject matter and may want renaming, or it is a new *windows-shell-tool-traps* page).
  Cross-reference from `kb/dev/android-device-verification.md`'s render-pass material, since that
  is the duty it breaks.
- **Anchors:** `kb/dev/look-at-your-own-output.md` (§4k — print the count beside the claim) ·
  `kb/dev/powershell-encoding-traps.md` · `kb/dev/android-device-verification.md` §6
- **Supersedes:** nothing. ⚠️ **An earlier draft of this very entry, written an hour before the
  probe, claimed *"adb pull from Git Bash reports success and writes nothing"* and blamed `adb`.
  That was wrong** — `adb` wrote the file it was told to write, and the fault is one layer up in
  the quoting. Recorded because the wrong version was the plausible one, and it would have sent the
  next reader hunting a device tool.
- **Status:** ready

## 2. `showSnackbar` suspends, so a notice consumed after it returns goes silent on the second refusal

**Claim.** The idiomatic-looking

```kotlin
LaunchedEffect(notice) { snackbarHostState.showSnackbar(text); onConsumed() }
```

leaves the notice **on the state for the whole time the bar is up** (4 s at `SnackbarDuration.Short`),
because `showSnackbar` suspends until the bar is dismissed. If a second, **equal** notice arrives in
that window, `LaunchedEffect`'s key does not change, the effect never restarts, and **the second
event is silent**. Consuming it *before* `showSnackbar` does not work either: the notice becomes
`null`, the `let` block leaves composition, and the effect is cancelled — taking the bar with it.

**The shape that works** is two effects, with a local copy in between:

```kotlin
var showing by remember { mutableStateOf<String?>(null) }
state.notice?.let { n -> LaunchedEffect(n) { showing = textOf(n); onConsumed() } }
showing?.let { t -> LaunchedEffect(t) { snackbarHostState.showSnackbar(t); showing = null } }
```

The state round-trips through `null`, so an identical event is a new one.

`Observed:` 2026-08-23, GoalPilot `#68`. It surfaced as an **instrumented test failing on the
consumption assertion**, not as anything visible — the first refusal renders perfectly, and the
defect is only in the second one. The product rule it violates is that app's §0.4, *legal but never
silent*; the general form is that a repeated identical event is dropped by any `LaunchedEffect`
keyed on a value class.

**Why.** Considered and rejected: *"make the notice carry a nonce/id so equal values differ"* — it
works, but it puts a field on a domain-ish type purely to defeat structural equality, and the next
person deletes it as unused. *"use a `Channel`/`SharedFlow` for one-shot events"* — the correct
answer in general, but it changes the state shape and loses the message across rotation, which was
wanted here.

- **Destination:** `kb/dev/` — a new page, or a section on whichever page holds Compose one-shot-event
  material. Working title: *one-shot events and the suspend that outlives them*.
- **Anchors:** none in the bundle today.
- **Supersedes:** nothing.
- **Status:** ready

## 3. The instrumentation component carries the build-type suffix, and `AGENTS.md`'s recipe elides it

**Claim.** In this repo `am instrument` must be given
**`com.idomarhaim.goalpilot.debug.test/com.idomarhaim.goalpilot.HiltTestRunner`**. The debug build
sets `applicationIdSuffix = ".debug"` (`app/build.gradle.kts:89`), so the test package is
`<applicationId><suffix>.test` — **not** `<applicationId>.test`.

`Observed:` 2026-08-23. `AGENTS.md`'s *Common commands* block writes the recipe as
`adb shell am instrument -w <appId>.test/<runner>`, which reads naturally as the `applicationId`,
and that spelling fails with

```
INSTRUMENTATION_FAILED: com.idomarhaim.goalpilot.test/com.idomarhaim.goalpilot.HiltTestRunner
Unable to find instrumentation info for: ComponentInfo{...}
```

**`adb shell pm list instrumentation` answers it in one command** and is the thing to run rather
than to guess — it prints the component and its target.

**Why.** The `install -r` + `am instrument` path is now the *recommended* one in this repo (it is
what preserves a Google sign-in that `connectedDebugAndroidTest` would destroy), so every session
that follows the sign-in guidance meets this. It is a cheap failure — one command, one clear error
— but it is a **stop** in the middle of the device pass, which is the expensive place to be
stopped. Considered and rejected: *"just say `.debug`"* — the durable fact is the **suffix rule**
plus the `pm list instrumentation` habit, which survives a release-variant run and a suffix change.

- **Destination:** `kb/dev/android-device-verification.md` §8, beside the `install -r` recipe it
  already carries.
- **Anchors:** `kb/dev/android-device-verification.md` §8 · this repo's `AGENTS.md` *Common commands*
- **Supersedes:** nothing — it **adds** to §8's recipe rather than contradicting it.
- **Status:** ready. ⚠️ The corresponding one-line correction to this repo's `AGENTS.md` is a
  **commons write** (leased path) and is **not** made by this session — flagged for whoever holds
  that lease next.

## 4. Clamp before you snap, when the range's ends are not on the grain

**Claim.** Rounding a value to a grain and *then* clamping it into a range can leave the result off
the grain, because a range end need not be a multiple of the grain. Clamping first and snapping
afterwards (with one final coerce) cannot.

`Observed:` 2026-08-23, GoalPilot `#68`'s drag landing arithmetic — the drawn grid ends at 23:00 and
the last legal block start is `23:00 − grain`, which is on the grain at 15 minutes and **off** it at
20. Caught by writing the test with a 20-minute grain rather than the shipped 15, which is the only
reason the ordering was ever exercised.

**Why.** Thin on its own, and recorded mainly for the **test** lesson rather than the arithmetic
one: a property that holds at the shipped constant and fails at a neighbouring one is invisible to
every test that uses the shipped constant. The generalisable rule is *parameterise the constant in
the test even when the product has only one value for it*.

- **Destination:** `kb/dev/look-at-your-own-output.md`, as a short instance under its
  *check the instrument on the hardest input it exists for* material.
- **Anchors:** `kb/dev/look-at-your-own-output.md`
- **Supersedes:** nothing.
- **Status:** ready, but **low value** — merge into an existing section rather than giving it a page.
