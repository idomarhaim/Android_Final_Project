## 2. `showSnackbar` suspends, so an EQUAL second event is silently dropped — and this narrows a standing KB claim

🛑 **ALWAYS-ASK IN BOTH MODES. NOT INGESTED, NOT STRUCK.** It contradicts a committed claim, and
`/kb-ingest` §3 would rewrite that claim in place — which is a deletion of committed knowledge.
**It needs Ido's word.**

**What it contradicts.** `C:\Dev\JARVIS\kb\dev\screen-entry-effects-and-viewmodel-lifetime.md` §4a
prescribes **await first, consume after** for a one-shot event delivered as nullable state, and
answers the obvious objection — *what about a second event queueing behind a long snackbar?* — like
this, verbatim:

> **That motivating concern is real, and the key already answers it.** A new event changes the key,
> restarting the effect, which dismisses the stale snackbar and shows the current one.

**That is true for a *distinct* second event and false for a *structurally equal* one**, which is
the case §4a's own reasoning does not separate.

**Claim.** `showSnackbar` suspends for the whole time the bar is up (4 s at
`SnackbarDuration.Short`), so with *await first, consume after* the event sits on the state
throughout. If a second, **equal** event arrives in that window, `LaunchedEffect`'s key does not
change, the effect never restarts, and the second event is **never shown**. Consuming *before*
`showSnackbar` is the failure §4a already documents — the effect cancels itself. So neither ordering
of the single-effect shape is correct; the fix is structural:

```kotlin
var showing by remember { mutableStateOf<String?>(null) }
state.notice?.let { n -> LaunchedEffect(n) { showing = textOf(n); onConsumed() } }
showing?.let { t -> LaunchedEffect(t) { snackbarHostState.showSnackbar(t); showing = null } }
```

Two effects with a local copy between them. The state round-trips through `null`, so an identical
repeat **is** a new event; and the bar is driven by the local copy, so consuming early no longer
cancels the coroutine that renders it. Both directions satisfied at once.

`Observed:` 2026-08-23, GoalPilot [`#68`](https://github.com/idomarhaim/Android_Final_Project/issues/68).
Two identical `CalendarNotice.TooLarge(812, 500)` refusals — the second silent — under §0.4, which
forbids the app being silent about a refusal. It surfaced as an **instrumented test failing on the
consumption assertion**, not as anything visible: the first refusal renders perfectly and only the
second is wrong, so looking at the screen does not catch it either.

**Why (what was rejected).** *"Give the event a nonce so equal values differ"* — works, but adds a
field to a domain-ish type purely to defeat structural equality, and the next reader deletes it as
unused. *"Use a `Channel`/`SharedFlow` for one-shot events"* — the right answer in general, but it
changes the state shape and loses the message across rotation, which was wanted here.

## 4. Clamp before you snap, when the range's ends are not on the grain

**Claim.** Rounding a value to a grain and *then* clamping it into a range can leave the result off
the grain, because a range end need not be a multiple of the grain. Clamping first and snapping
afterwards (with one final coerce) cannot.

`Observed:` 2026-08-23, GoalPilot `#68`'s drag-landing arithmetic — the drawn grid ends at 23:00 and
the last legal block start is `23:00 − grain`, which is on the grain at 15 minutes and **off** it at
20. Caught by writing the test with a **20-minute** grain rather than the shipped 15, which is the
only reason the ordering was ever exercised.

**Why.** Thin as arithmetic, and recorded for the **test** lesson instead: a property that holds at
the shipped constant and fails at a neighbouring one is invisible to every test that uses the
shipped constant. The generalisable rule is *parameterise the constant in the test even when the
product has only one value for it*.
