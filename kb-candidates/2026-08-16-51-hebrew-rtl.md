## 1 · Android's Hebrew resource bucket is `values-iw`, and every explanation of why is wrong

- **Claim.** Hebrew string resources must live in `res/values-iw/`; `values-he/`
  compiles, ships, reviews as done and **renders nothing**. The cause is the
  **resource system alone** — AAPT2 stores Hebrew under the legacy qualifier
  `iw` and does not fold `he` into it. It is **not** caused by `Locale`
  reporting `iw`, which is the explanation given in every tutorial, in this
  ticket's first draft, and in this session's own first three commits' worth of
  KDoc.

- **The measurements, because this was got wrong twice before it was got right.**
  1. `Observed:` JDK 21.0.12, 2026-08-16 — every constructor
     (`Locale.forLanguageTag("he"/"iw")`, `Locale.of("iw")`, deprecated
     `Locale("iw")`) returns `language=he`. JDK 17 flipped
     `java.locale.useOldISOCodes` to `false`, dropping `he→iw`, `yi→ji`, `id→in`.
  2. **First correction, and it was still wrong:** *"…but Android's libcore kept
     the mapping."* `Observed:` Android 17 / API 37 emulator, 2026-08-16 —
     `Locale.forLanguageTag("he").language` returns **`"he"`** there too.
  3. **And yet `values-iw/` resolves correctly on that same device.**
     `Observed:` same run — a Hebrew-configured context returned the Hebrew text
     for all nine translated keys, and reported `LAYOUT_DIRECTION_RTL`. So the
     bucket works while the supposed reason for it is false.
  4. Prior device evidence for the failure itself: 2026-08-16, session
     `widget-pack`, Samsung SM-S938B at `he-IL` — `values-he` strings rendered
     English, `aapt2 dump` of the on-device APK listed `he` **and** `iw` as
     separate buckets.

- **Why the folk explanation is worse than no explanation: it is self-defeating
  as it ages.** It names a checkable fact (`getLanguage()`), that fact has now
  flipped, and checking it returns `"he"` — which reads as *"the legacy wart is
  gone, this directory name is stale, rename it to `values-he`"*. The
  measurement that appears to authorise the rename is the measurement that
  causes the outage. An explanation that invites a check whose modern answer
  points the wrong way is a **trap**, not a simplification.

- **Consequences.**
  1. The on-device tell for the underlying defect is the **split signal**: the
     layout mirrors correctly to RTL while the text stays English — the host
     knew the device was Hebrew and the string lookup did not.
  2. **The obvious unit test cannot exist.** `assertThat(Locale…language)`
     `.isEqualTo("iw")` fails on the JVM; `.isEqualTo("he")` pins something true,
     irrelevant and misleading. Both are worse than nothing. What is asserted
     instead is `isAnyOf("he", "iw")` **with a message saying nothing may branch
     on it** — a test whose purpose is to forbid a dependency rather than pin a
     value.
  3. Any code deriving behaviour from `locale.language` (an RTL lookup table, a
     bucket-name computation, a cache key) is fragile in both directions.

- **The remedy, and the rejected ones.** *Declare* language-dependent facts on
  the enum constant (`HEBREW(isRtl = true)`) rather than computing them from
  `Locale`; pin the bucket with a **directory-existence** test, which is
  platform-independent; and prove the actual lookup in `androidTest`, the only
  layer that can. **Rejected:** (a) an RTL table carrying both spellings — works
  today, one platform change from silently returning `false`; (b) asserting the
  device answer in a unit test and excluding it from CI — a test that must be
  skipped is a comment.

- **The two general rules this is an instance of.**
  1. *A JVM unit test is not a weaker device test.* On locale, resources and
     anything else libcore diverges on, it is a test of a **different system**
     that answers confidently and wrongly. Pick the layer that can observe the
     behaviour.
  2. *Record the fact you depend on, not the story you tell about it.* The
     conclusion (`values-iw`) survived three rounds of measurement; the causal
     story was falsified twice. Documentation that leads with the mechanism ages
     into an instruction to break the thing it was protecting.

- **Destination.** `kb/dev/` — new page, e.g.
  `kb/dev/jvm-vs-android-locale-codes.md`. Cross-links to the
  *look-at-your-own-output* page (the instrument degrading silently on exactly
  the input it exists for) and to `kb/dev/enum-and-label.md` (declare, don't
  derive).
- **Anchors.** `app/src/main/java/com/idomarhaim/goalpilot/domain/model/AppLanguage.kt`
  (`locale` KDoc), `app/src/test/java/com/idomarhaim/goalpilot/domain/model/AppLanguageTest.kt`
  (KDoc + `the runtimes disagree…` test),
  `app/src/test/java/com/idomarhaim/goalpilot/resources/HebrewLocaleResourceTest.kt`.
  Prior device evidence: commit `a4e5c36`, `SESSIONS.md` `widget-pack` note of
  2026-08-16, `WidgetHebrewResourceTest` KDoc.
- **Supersedes.** Nothing. **Extends** `widget-pack`'s device finding by giving
  the *mechanism* (the JDK 17 flag) and by adding the JVM half, which
  `widget-pack` had no reason to look at.

## 2 · An untranslatable string is recognised by a rule, not by an allowlist

- **Claim.** When guarding "no Hebrew string is an untranslated copy of its
  English original", the two legitimate exceptions are exempted by *what makes
  them exceptional*, not by being listed: a string with **no letters left once
  format specifiers are stripped** (`%1$d%%`) is untranslatable by construction,
  and a string that does carry words but is language-independent (a brand name)
  is what aapt's own `translatable="false"` is for — which also, correctly,
  excuses it from the parity check.

- **Why.** The first draft used a hand-maintained `SAME_IN_BOTH` set. It needs a
  human decision per string forever, and every future format-only string is a
  false positive. **The subtlety that makes this worth a page:** the naive
  version of the rule — "does it contain any letter?" — **is wrong**, because
  `%1$d` contains the letter `d`. `Observed:` the test failed on
  `gp_widget_percent` = `%1$d%%` with a `\p{L}` check. The specifiers must be
  stripped *first*. That is a one-line bug that reads as correct.

- **Destination.** `kb/dev/` — a section on an i18n/resource-testing page, or
  folded into the page from entry 1.
- **Anchors.** `HebrewLocaleResourceTest.carriesWords` and its `SPECIFIER` regex.
- **Supersedes.** Nothing.
- **Status.** Pending — `kb/`-destined, cross-repo.

## 3 · `values-he` was dead for a day, and the board note is why it was caught

- **Claim.** Issue #36 shipped `res/values-he/strings.xml` on 2026-08-15. It
  never rendered once. It was found not by a test or a review but by a **cross-
  session board note** — `widget-pack` hit the defect in its own file on a
  device, wrote *"`36-tasks-consent`: this is yours too"* on `SESSIONS.md`, and
  named the other session's file explicitly rather than only fixing its own.

- **Why it matters.** The defect class is *silent and reviews as done*, so the
  normal discovery paths (tests, code review, the author re-reading their own
  diff) are all structurally blind to it. The thing that actually worked was a
  session **generalising its own device finding to code it did not own** and
  writing it where the next session would read it. Worth recording as evidence
  for the board-note practice, which otherwise only ever gets cited for conflict
  avoidance.

- **Destination.** `kb/dev/flows/` or the session-board page — as an instance,
  not a new rule.
- **Anchors.** `SESSIONS.md` `widget-pack` note 2026-08-16 (`⚠️ … values-he/
  SILENTLY DOES NOTHING`); commits `fba4197` (the defect), `a4e5c36` (the
  finding), this session's move to `values-iw/`.
- **Supersedes.** Nothing.
- **Status.** Pending.
