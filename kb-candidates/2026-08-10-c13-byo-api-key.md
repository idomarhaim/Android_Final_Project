## 1. "I don't understand the options" can mean the question was never the user's to answer

**Claim.** When a user answers a question picker with *"I could not understand you — you choose"*, the first thing to test is not whether the axis was reduced far enough, but **whether the decision turns on anything only that user knows**. If it does not, the refusal is correct and the fault is that the question was asked at all.

**Why.** This is the **third** instance of the same surface symptom in one repo, and the first two produced a different diagnosis that this instance falsifies as a complete explanation.

- Instances 1 and 2 (`entity-model-intake`, `c10-quote-feed`, both 2026-08-09/10) concluded: *every option shared a framing the user does not hold* → fix = **reduce the axis, and state it before the picker**.
- Instance 3 (this session) **applied that fix in full** — every question named its axis, named the axes considered and dropped, and three of four carried per-option previews — and the symptom recurred on **3 of 4** questions.

The discriminator is visible in *which* question survived. Nine questions were put across two pickers:

| answered fluently | refused |
|---|---|
| does the key change the pipeline or the credential | must each adapter enforce the schema natively |
| where does my secret live at rest | what does the "once" latch reset on |
| which providers do I want | one switch or four |
| which provider list, and does adding one cost a deploy | |

Everything in the left column turns on the user's own values, risk appetite or preferences. Everything in the right column turns on engineering quality and could be answered correctly by anyone holding the codebase and the measurements — which is precisely the class the **derivable-decision rule** already says to derive and log rather than ask. He said so himself, in the same breath: *"choose the solution that gives the highest standard and quality of the app… and if you think there is a way to improve it, improve it."*

**A sibling session hit the same surface on the same day, with a *different* underlying fault — which is the strongest evidence that one diagnosis was never going to cover it.** `c16-milestone-model` (2026-08-10, `#37`) recorded: *"this session's own question was the bug"* — it offered three options with a diagram each, Ido could not answer, and the reason was that **none of the three was right**; reframing produced a fourth answer better than all of them. That is a *coverage* failure — the correct answer was outside the option set. This session's is an *ownership* failure — the correct answer was outside the **user**. Same symptom, same day, same repo, two unrelated causes. So the picker has at least three failure modes on record (framing, coverage, ownership) and "reduce the axis" addresses one.

**Rejected reading:** that this is a fourth corroboration of "unreduced axis". It is not — the axis fix was applied and the symptom persisted, so treating it as corroboration would keep sharpening a tool that had already been sharpened, on a failure it does not cut.

**What this changes in practice, and it is a pre-filter, not a replacement:** before drafting a picker, sort the candidate questions into *turns on the user* and *turns on the artifact*. Only the first group gets asked; the second is derived, logged, and **shown** — because the user still needs to be able to overturn it. Both fixes are live: the axis test still applies to everything that survives the sort.

**Destination.** Sharpens the standing entry, which is itself parked: `entity-model-intake` #1 (*"it doesn't understand me usually means every option shares a framing the user doesn't hold"*), whose target is the `rules/question-axis-naming.md` draft at `C:\Dev\JARVIS\rules\`.

## 2. The "different mechanism" test applies to the *enhanced* path, not only the degraded one

**Claim.** When choosing between two designs, the one that grows a **second implementation of the same logic** loses — and the second implementation is just as dangerous when it sits on the *better* path as on the *worse* one. The question is not "which branch is the fallback" but **"which branch is rarely exercised"**.

**Why.** `C10` decided the quote feed by comparing degraded modes: the rejected design fell back into a *different mechanism*, a second implementation run only when nobody was watching. `C13` faced the mirror image and the same test decided it, pointing the other way.

- A user-supplied key that makes the **client** call the provider directly needs a second copy of every prompt and every output schema, because the first copy lives server-side in the Cloud Function.
- That second copy is on the **premium** path. It runs only when a key is present — which, for a single-user app, is exactly when no test, no other user and no CI ever exercises it.
- So the key was made to ride **to the existing proxy** as a credential instead. One set of prompts, one set of schemas, one fallback ladder; the only thing that varies is which credential and which adapter the single pipeline uses.

**Rejected:** the device-direct design, whose genuine advantage — the secret never leaves the phone — was real and was still outvoted. That is what makes the entry worth keeping: the mechanism-count argument beat a **security** argument, not merely a convenience one.

**Destination.** Central KB — folds as a new § into the existing page created from `c10-quote-feed`'s ingest (*"between two close designs the fallback shape decides, because a different-mechanism fallback is a second implementation run only when nobody is watching"*), generalising its rule from *fallback* to *rarely-exercised branch*. Locate that page by title before writing; do not create a second page on the same claim.

**Anchors.** `CHANGELOG/2026-08-10/c13-byo-api-key.md` §*The decision*; [#32 resolution comment](https://github.com/idomarhaim/Android_Final_Project/issues/32); `CHANGELOG/2026-08-10/c10-quote-feed.md`.

## 3. Schema enforcement and value validation catch disjoint failure classes; neither substitutes for the other

**Claim.** A provider's native structured-output feature guarantees the **shape** of a reply. It cannot guarantee that the **values inside** the shape are ones you sent or ones that exist. Those are different failures, and a design that adopts native enforcement and drops its own validation has traded a check for a guarantee that does not cover the same ground.

**Why.** Measured, not reasoned. A 248-call probe of one model (`openai/gpt-oss-20b`, production temperature, Hebrew and English) produced 170/170 clean JSON parses and 168/170 valid on every field — and its **single** failure mode was an id supplied as `8xKq2mN4vRt7pLwZaB1c` coming back as `8xKq2mN4vRt7pLwZaB`: correct type, plausible length, correct character class, **not a member of the list sent with it**. Every structural check passes. No JSON Schema, `response_format`, `responseSchema` or forced tool-use can express "must be one of the values in the prompt", so no provider and no model size closes it.

| failure | example | caught by |
|---|---|---|
| structural | a missing field, `"type": "BANANA"` | native enforcement |
| **semantic** | an id of the right type and shape that was never sent | **value validation only** |

**Rejected:** *"strict schema everywhere, so the validation layer can go"* — which is the natural conclusion once every provider is required to enforce natively, and which would have removed the only thing that catches the one failure actually observed.

**Destination.** Central KB — a new § on the existing structured-output page (which already carries a §2.1 on making a corruption *unreachable* by not sending the token at all, and a § from `c7-what-is-a-unit`). This entry is the case where the token **must** be sent, so unreachability is unavailable and checking is the whole defence.

## 4. Widening the provider set re-prices every guarantee that guards against a swap

**Claim.** A safeguard's value is set by how often the event it guards against occurs. So a decision that makes a rare event **routine** silently promotes every optional guarantee against it into a requirement — and that promotion is a *consequence* of the widening decision, which means it should be priced at the moment the set is widened, not discovered later by whoever inherits the format spec.

**Why.** A probe concluded that strict `json_schema` *"buys a guarantee that survives a model swap, not reliability"* — filed as a footnote, correctly, because the app had exactly one pinned model and a swap was a once-a-year event. A later decision let the user supply a key for any of **four** providers. Nothing about the schema changed and nothing new was measured, yet the footnote became load-bearing: with four providers a model swap is the **normal case**, so a format expressible only as prose-in-the-prompt stopped being adoptable.

The same re-pricing ran in reverse and settled a second question for free: requiring native enforcement costs **nothing** once the provider list is closed to four that all have it, and would have excluded exactly one candidate — the "any OpenAI-compatible base URL" slot. So "which providers" and "what must each guarantee" turned out to be **one decision seen twice**, and answering them independently would have let them contradict.

**Rejected:** treating the provider list as a product/UX question and the schema contract as an engineering question, i.e. as independent. They share a single variable — how much of the model space the app must be correct across.

**Destination.** Central KB — a general design page, most likely folding into the existing decision-map/charting page, since the transferable form is *"a decision that widens a set re-prices the guarantees over that set; look for the second question it has silently answered."* Check that page for an existing § before creating a new page.
