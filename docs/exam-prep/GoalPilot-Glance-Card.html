1 · The product - what it is and why

1In one minute: what is GoalPilot?
  • Life goals, not a to-do list
  • 3 levels: track → recommend → motivate
  • Life areas → goals → tasks
  • LLM files a task, scores it, estimates minutes
  • Points → levels → friends leaderboard
The donut answers which part of my life am I actually spending it on?
2What is the difference between a life area, a goal, a task, and an occurrence?
  • Life area = your division of your life
  • Goal = filed under exactly one area
  • Task = hangs off goals via goalEdges (can serve several)
  • Occurrence = one instance of a repeating task
  • Occurrences generated, not stored — only ones you touched
Otherwise a fortnightly task is 26 documents a year.
3Which features are the core requirement and which are bonus?
  • Core: sign-in, goals, tasks+points, progress, image upload, sharing, leaderboard, AI, levels
  • Bonus: LLM classification, time donut, animated charts
  • Nice-to-have: Google Tasks, Health Connect, Calendar, 5 widgets, BYO key, tour, 7 theme axes
  • Challenges = architected, not finished
4How do points and levels work?
  • Points from difficulty, or the LLM
  • pointsForLevel(n) = 50·(n−1)·n
  • L2 = 100, L10 = 4,500 — quadratic
  • level / progress / toNext all derived
  • points stored — a reader can't compute it
Store a derived number only when the reader can't see the facts behind it.
5What is the friend code, and why not just use the user's UID?
  • UID = 28 chars, unusable across a table
  • 6-char code, allocated on first sign-in
  • Mirrored onto publicProfiles so it resolves
  • No public profile → addFriend rejects
So a mistyped code can never write a dangling friend edge.
6Where did the requirements come from, and how do you know you met them?
  • Course spec + my own UX review notes
  • Transcribed with stable ids R1–R28, E1–E19
  • Cited from issues, TODO/, PRODUCT_v0.3.md
Every screen decision traces to a numbered line, not to memory.

2 · Architecture and layering

7Describe the architecture.
  • One module, 4 bands — see the diagram
  • feature + ui + notifications → domain ← data
  • domain/ has no Android, no Firebase
  • di/ = 3 Hilt modules, the only seam
Every arrow points inward and none points out.
8Why MVVM, and not MVC, MVP or MVI?
  • ViewModel survives config change — platform gives it
  • Compose wants one observable state object
  • MVP needs a view interface per screen = dead weight
  • Actually MVVM with an MVI-shaped state
  • No reducer: VM functions are already the only mutation points
9Why do repository interfaces live in domain/ and implementations in data/?
  • Dependency inversion
  • Domain compiles with no Android/Firebase on classpath
  • VM test = mock into the constructor, no emulator
  • 14 interfaces; RepositoryModule binds them all
Swapping Firestore would be a change in one package.
10What is a use case, and when do you add one instead of putting the logic in a ViewModel?
  • Pure, injectable, no Android
  • When: non-trivial · shared · worth testing alone
  • TimeAllocationUseCase, ReorderLifeAreas, Leveling
  • Reorder returns the minimal sortOrder map
One drag writes the span it crossed, not the collection.
11Why one Gradle module rather than a multi-module project?
  • Split buys build time + enforcement
  • Only enforcement was ever the issue here
  • Build is fast enough; wiring cost not worth it
  • Cost I accept: layering is convention, not compile error
:domain is the first module I'd extract — it already has zero Android deps.
12What is Resource<T>, and why not just throw exceptions?
  • Sealed: Loading / Success<T> / Error
  • Loading is a real UI state — an exception can't express it
  • Errors get rendered, not caught
  • Sealed → compiler checks the when
  • Flows use .catch { } instead
13Why are there DTOs as well as domain models?
  • Firestore needs var + no-arg defaults + @DocumentId
  • Domain models are immutable with real invariants
  • Incompatible → map at the repository boundary
  • Pays off in migration: DTO absorbs old + new shape
3 migration tests pin it, so a document from months ago still reads.

3 · Jetpack Compose and the UI

14Why Compose instead of XML layouts?
  • Screen = function of state → no view/model drift
  • No notifyDataSetChanged bug class at all
  • ~24 composables, zero custom View, zero Adapter
  • 7 theme axes live = a CompositionLocal, not styles
Cost: you must understand recomposition, or you write code that's correct and slow.
15What is recomposition, and what triggers it?
  • Compose tracks which composables read which State
  • State changes → only those re-run
  • Runs often → body must be cheap, no side effects
  • Can be skipped (stable params) and reordered / parallel
  • Side effects → LaunchedEffect / DisposableEffect
16remember vs rememberSaveable vs ViewModel - when do you use each?
  • remember — recomposition only (scroll, expanded flag)
  • rememberSaveable — + config change + process death (text field)
  • ViewModel — + scoped to nav entry, anything with a repository
Lose it on rotation and it's a bug? Not remember. Needs a repository? Not rememberSaveable.
17What is state hoisting? Show me where you did it.
  • State out; value in, onValueChange out
  • Every screen hoisted to its ViewModel
  • Screen takes UiState + lambdas
  • LifeAreaRows.kt — rows as a LazyListScope extension
That's why a UI test can drive a screen with no Firebase in the room.
18How do you avoid unnecessary recomposition?
  • Keep state low → invalidation stays local
  • Pass stable types so Compose can skip
  • Stable key on LazyColumn items
  • Never a lambda where a value would do
BarItem carries countSuffix: String, not a formatter lambda — two identical lambdas aren't equals, so the chart restarted its animation forever.
19Your charts animate when they appear. Why couldn't you use animateFloatAsState?
  • It initialises at its target
  • No previous value on first composition
  • → a value that never changes never animates
  • Fix: Animatable explicitly started at 0f
  • rememberChartProgress in ChartAnimation.kt
The analytics screen used to just appear fully formed.
20How does navigation work?
  • Navigation-Compose, one NavHost, routes in one Routes object
  • Two graphs chosen by auth state
  • 4 tabs: Home / Goals / Calendar / Social
  • Profile is an avatar, not a tab — 5 is crowded
  • Required id in the path; optional as a query arg
A nullable arg would compile 'a life area with no area' into every caller.
21How does theming work, and why is Material You dynamic colour switched off?
  • 7 independent axes, each a pure enum in domain/model/
  • PaletteTransform composes them; 4 full ColorSchemes
  • Device-local SharedPreferences as a hot StateFlow
  • First frame already has the right palette
Dynamic colour lets the wallpaper decide every colour — two colour authorities can't both win.
22How do you know your colours are readable?
  • ThemePaletteTest — WCAG contrast, all 4 schemes
  • + pairwise distinctness of 10 category colours
  • A bad hex fails the build
Where a design rule can be an assertion, it's a test, not a comment.
23Is the app accessible?
  • Contrast test-enforced
  • contentDescription via Modifier.semantics; donut describes its slices
  • All dp, scales with font size — checked on a real S25 Ultra
  • Not done: full TalkBack pass
24Tell me about the first-run tutorial.
  • Spotlight overlay, 7 steps, skippable + replayable
  • One step waits for you to open Goals yourself
  • Screens only tag Modifier.tutorialAnchor(...)
  • TutorialStepsTest asserts every anchor exists
What no test can check is whether a step's sentence is still true — it keeps rendering perfectly and starts lying.

4 · State, coroutines and Flow

25Describe your state pattern.
  • One immutable StateFlow<UiState> per screen
  • combine(...).stateIn(viewModelScope, WhileSubscribed(5s), initial)
  • Screens stateless: collectAsStateWithLifecycle()
  • State down, events up
26What is SharingStarted.WhileSubscribed(5000) and why five seconds?
  • Keeps upstream alive 5 s after the last collector
  • Chosen for rotation — collector dies and returns in ms
  • Eagerly → listeners open in the background, billing reads
  • Lazily → never restarts cleanly
Long enough to span a rotation, short enough not to span a real backgrounding.
27Flow vs StateFlow vs SharedFlow - when do you use which?
  • Flow — cold, per-collector. Repositories return these
  • StateFlow — hot, has a current value, conflates = state
  • SharedFlow — hot, no current value, replay = events
  • One-shots go through the state + an explicit consume
So a rotation can't re-fire a snackbar.
28Why collectAsStateWithLifecycle() and not collectAsState()?
  • collectAsState keeps collecting in the background
  • Lifecycle version stops at STOPPED
  • With Firestore that's real money and battery
  • Pairs with WhileSubscribed(5000) to actually tear down
29How does a Firestore snapshot listener become a Kotlin Flow?
  • callbackFlow + addSnapshotListener
  • trySend each snapshot, close on error
  • `awaitClose { registration.remove() }`
A callbackFlow without awaitClose throws — Kotlin protecting you from exactly that leak.
30Your repositories build their flows on a UID flow and flatMapLatest. Why?
  • A Flow is built when the ViewModel is created
  • Reading auth.currentUser once pins that account
  • Build on uidFlow() + flatMapLatest instead
  • UID changes → old query cancelled, new one starts
Otherwise, demo sharing with two accounts and you serve A's goals to B.
31Where do you switch dispatchers?
  • DispatchersModule injects them — substitutable in tests
  • Firebase already does its own I/O off-main (.await())
  • Default for CPU work: calendar window, time rollup
32What happens to an in-flight coroutine when the user rotates the screen?
  • Nothing — viewModelScope is tied to the ViewModel
  • ViewModel survives config change
  • Save completes, result lands in the state
That's why it's not a LaunchedEffect — that would be cancelled mid-save.
33What is structured concurrency, and where does it show up in your code?
  • Every coroutine has a parent; cancel parent → cancel children
  • viewModelScope parents everything a screen starts
  • callbackFlow torn down by the same cancellation
  • WorkManager is the deliberate exception — must outlive the process
There is no manual lifecycle bookkeeping anywhere — nothing unregisters in onDestroy.

5 · Dependency injection with Hilt

34What is Hilt, and why use dependency injection at all?
  • Compile-time DI over Dagger, via KSP
  • Missing binding = compile error, not a crash
  • Dependencies explicit in the constructor
  • Lifetimes scoped, not scattered singletons
And it's what makes the ViewModels testable with plain mocks.
35Which Hilt modules do you have?
  • FirebaseModule — @Provides the Firebase singletons
  • RepositoryModule — @Binds interface → impl
  • DispatchersModule — dispatchers behind qualifiers
  • @HiltAndroidApp / @AndroidEntryPoint / @HiltViewModel
36@Binds versus @Provides - what is the difference and why did you use each?
  • @Provides — a method body that builds it (Firebase factories)
  • @Binds — abstract, 'this interface → that impl'
  • @Binds generates less, needs a constructor-injectable impl
  • Every repository impl here is one
37How does a ViewModel get its dependencies inside a composable?
  • hiltViewModel()
  • Resolves the owner from the NavBackStackEntry
  • → scoped to the navigation destination
  • Navigate away and back = fresh; rotate = same
Activity-scoped instead, and two goal-detail screens would share one ViewModel.
38Why is AppPreferencesRepository field-injected into MainActivity rather than read through a ViewModel?
  • Skin must be known outside GoalPilotTheme
  • Every hiltViewModel() lives inside it
  • So @Inject lateinit var on the Activity
  • Hot StateFlow over SharedPreferences
Otherwise the first frame flashes the default palette and then corrects.
39How does DI help your tests?
  • JVM tests use no Hilt — construct the VM with mockk fakes
  • Possible only because every dep is a constructor interface
  • Instrumented tests do: HiltTestRunner + @HiltAndroidTest
  • Test module replaces a real one → no network

6 · Firebase, the data model, and offline

40Draw your Firestore data model.
  • Everything private under users/{uid} — one rule covers the subtree
  • goals → progress; tasks; completionFacts; occurrences; lifeAreas
  • publicProfiles — world-readable projection
  • shares, challenges/{id}/participants/{uid}
Anything another user must see is a deliberate, minimal projection.
41Why Firestore and not Room or SQLite?
  • Requirement is multi-user — leaderboard, shared summaries
  • Local DB would need a server anyway
  • Get auth + per-document rules + realtime + offline in one dep
  • Cost: no joins, no SQL
Relational work happens client-side — the friends leaderboard fetches by document id.
42Does the app work offline?
  • Yes, designed for it — cache serves reads, queues writes
  • Tick, edit, log progress all work with the radio off
  • Honesty about staleness: an as-of stamp, not a banner
  • LLM → local fallback; widget → cached snapshot
43What happens when the user completes a task? Walk me through the write.
  • One document write
  • set on completionFacts/{taskId} (delete to untick)
  • Client sums its own points on device → instant
  • projection.ts totals onto publicProfiles.points
One write, not a transaction — and it works with the radio off.
44Why did you remove the transaction? Wasn't that less safe?
  • A transaction cannot be served from the cache
  • Offline: hung, then failed after 7.9 s (measured)
  • set on a known path is idempotent — no read-modify-write
  • Sum moved to a Cloud Function; rules block client writes to points
It got more correct and more available at the same time.
45There used to be a level field. Where did it go?
  • Deleted. Derive, don't store
  • Pure function of points, in the same document
  • Every reader could already compute it
  • Stored → a second number that can disagree
46Why is points the one derived number that IS stored?
  • It's the only one a reader can't compute
  • Leaderboard shows another user's points
  • Their tasks are owner-only — you can never see them
  • 5 of 7 candidates failed that test and were deleted
Store it only when the reader can't see the facts it comes from.
47How does the leaderboard work?
  • Everyone: publicProfiles ordered by points, cap 100
  • Friends: fetch by document id, whereIn, chunked at 30
  • Ranking after filtering, in a pure tested function
Filtering the global top-100 client-side would drop every friend outside it — which is most friends.
48Deleting a goal - does it cascade?
  • Firestore has no server-side cascade — the client batches it
  • progress batch-deleted; tasks unlinked, not deleted
  • A task can serve several goals via goalEdges
  • Life area: clear lifeAreaId first, then delete
In that order so a failure leaves the area alive — retryable — not goals pointing at nothing.
49How does image upload work?
  • Picker → content Uri → StorageRepository
  • Path from StoragePaths, under the user's own prefix
  • Download URL stored on the progress doc
  • Coil AsyncImage for display + caching
storage.rules stops anyone uploading into another user's folder.
50What indexes does your app need?
  • Almost none — firestore.indexes.json is basically empty
  • Single-field indexes are automatic
  • Composite only for filter-on-X + order-by-Y
  • Life areas sorted client-side — a handful of docs
A judgement call about scale; I'd call it the other way for a collection that can grow.

7 · Security, rules and permissions

51Walk me through your Firestore security rules.
  • isSignedIn() + isOwner(uid)
  • users/{uid}/{document=**} → owner-only, whole subtree
  • publicProfiles → any signed-in reads; owner writes except `points`
  • shares → author only, checked on authorUid
  • challenges → owner-only; participants/{uid} subcollection
52How do you let someone join a challenge without letting them edit it?
  • A subcollection is not covered by its parent's match
  • Without its own block it matches no rule → denied
  • Challenge doc stays owner-only
  • Joining = writing your own participant row
  • 3 writers on that row, 3 different rights
53You have a rule function called serverOwns(field). Explain it.
  • Says: this write does not touch this field
  • diff().affectedKeys().hasAny([field])
  • Catches add, edit and removal; merge or whole doc
  • resource != null guard — set() evaluates create and update
Comparing the fields directly errors out when the key is absent — which denies for the wrong reason and reads like a bug in the logs.
54google-services.json is committed to the repository. Isn't that a secret?
  • No — project id + an Android API key
  • The key identifies, it doesn't authenticate
  • Restricted by package name + signing SHA-1
  • Real authorisation = Auth + rules, on the server
  • Not committed: local.properties, functions/.env
55Where does the LLM API key live?
  • functions/.env only — server side
  • Never in the APK
  • An APK is a zip; strings are strings
  • Callable → Firebase Auth already knows who's spending
That's the whole reason the LLM sits behind a Cloud Function.
56The user can bring their own AI key. Where is that stored?
  • EncryptedSharedPreferences, master key in the Android Keystore
  • Hardware-backed where the device supports it
  • Never Firestore; leaves the phone only to my own function
  • Firestore was cheaper and rejected on posture
A third-party secret at rest in someone else's database is a worse posture than the platform keystore.
57You keep allowBackup="true". Why not turn backup off?
  • Off would take theme, language, day schedule with it
  • Only the encrypted key file is excluded
  • Both schemes: fullBackupContent + dataExtractionRules
  • minSdk 26 → both are live
Its master key is in the device Keystore and doesn't travel — a restored copy would be undecryptable ciphertext, worse than absent.
58What runtime permissions does the app request, and why so few?
  • INTERNET, ACCESS_NETWORK_STATE (install-time)
  • POST_NOTIFICATIONS (runtime, API 33+)
  • Health READ_STEPS + READ_SLEEP only
  • No exact alarm — nothing needs the minute
  • No health write — read-only is load-bearing
USE_EXACT_ALARM asserts to Play that this is an alarm-clock app. It isn't.
59Why don't you ask for the notification permission at launch?
  • Android 13 stops showing it after two dismissals
  • So the first ask is nearly the only ask
  • Cold-launch prompt spends it before the app has done anything
  • NotificationPermissionPolicy waits for the first real outcome
Ask at the moment the user can see what it buys them.

8 · The AI integration

60How does the LLM integration work, end to end?
  • ViewModel → Firebase callable → provider → typed JSON
  • 4 callables: getRecommendations, classifyTask, scoreTask, proposeMeasure
  • All four surfaced in the UI — none is dead code
  • Client never talks to a model
61Why a Cloud Function proxy instead of calling the model from the app?
  • The key never ships
  • The caller is already authenticated
  • Prompt + schema server-side → change without an app update
  • Model id = one pin in one file
62What happens when the LLM call fails, or the phone is offline?
  • It degrades, never blocks
  • fallbackRecommendations / Classification / Points
  • Computed on device from the user's own data
  • UI says which it's showing
The AI is an enhancement to a product that has to work without it.
63Can the AI write to your database?
  • No. The model proposes, the app decides
  • Smart add always shows a confirm dialog
  • A suggestedGoalId matching nothing is discarded
  • AI supplies judgement; the app supplies arithmetic
Four layers between the model and the database: schema, clamp, id validation, your confirm.
64How do you handle a model being retired?
  • DEFAULT_MODEL — one pin, overridable by env var
  • Failure is silent: fallbacks serve, AI just looks bland
  • Pre-demo checklist: check the deprecation page
It fails bland, not broken — which is why it needs checking rather than monitoring.
65Why did classifyTask and scoreTask also return estimated minutes, rather than a second call?
  • GROQ free tier = 30 requests/minute
  • Google Tasks import already spends one per row
  • One wide call per feature, not several narrow ones
  • classifyTask also takes life areas → filed on arrival
66Bring-your-own-key supports exactly four providers. Why not any OpenAI-compatible endpoint?
  • 4 named adapters: GROQ, OpenAI, Anthropic, Gemini
  • 'Any endpoint + 3 text fields' was free — and lets an untested wire format run
  • 5th provider = a deploy, not a settings edit
  • Model id is free text with a default
A curated model list rots identically, and would now rot in four providers at once.

9 · Android platform fundamentals

67Walk me through the Activity lifecycle.
  • create → start → resume ⇄ pause → stop → destroy (+ restart)
  • Config change destroys and recreates → state in a ViewModel
  • Process can die while stopped → rememberSaveable
  • MainActivity is thin: edge-to-edge, deep link, update check, setContent
68You have a single Activity. Why, and what are the trade-offs?
  • Recommended with Navigation-Compose
  • One back stack, not two interleaved
  • Scaffold / bottom bar / tour wrap every screen once
  • Exception: HealthPermissionsRationaleActivity — the system launches it
An Activity outside the root gets no insets for free — it needs safeDrawingPadding().
69Why is MainActivity declared launchMode="singleTop"?
  • Notification tap-through
  • Already on top → intent goes to `onNewIntent`
  • No second copy of the app stacked on itself
  • So both onCreate and onNewIntent are handled
Handle only onCreate and you route the first tap of a session and silently ignore every one after.
70What is enableEdgeToEdge, and how do you handle insets?
  • App draws behind status + nav bars
  • Default on Android 15, mandatory at targetSdk 35
  • Only the root scaffold insets — once
  • windowSoftInputMode=adjustResize for the keyboard
71What is in your manifest, and why?
  • 5 permissions, 1 Activity + 1 exported rationale, 1 alias, <queries>, 5 widget receivers
  • <queries> — package filtering hides Health Connect on ≤13
  • Without it getSdkStatus() says UNAVAILABLE on a device that has it
  • One receiver per tile — the launcher lists receivers
72You have an <activity-alias>. What is that and why did you need one?
  • A second manifest entry pointing at an existing Activity
  • Own intent filters, own android:permission
  • Android 14 put the rationale behind VIEW_PERMISSION_USAGE
  • System requires START_VIEW_PERMISSION_USAGE on that component
Putting it on the Activity would also gate the ≤13 entry point, which may not be gated.
73How do you schedule reminders - WorkManager, AlarmManager, or a Service?
  • WorkManager — one job per reminder + an evening PlanTomorrowWorker
  • Not AlarmManager: nothing needs the minute; exact alarms need that permission
  • Not a Service: nothing continuous to do
  • Survives reboot + process death, respects Doze
There's no credential for a background sync and can't be — so every reminder is local or nothing.
74How do notifications work in your app?
  • GoalPilotChannels — channels are mandatory since Android 8
  • No channel → the notification is silently dropped
  • NotificationPermissionPolicy decides when to ask
  • NotificationDeepLink parks the intent in a StateFlow
The intent is resolved before the nav controller exists — so it's parked, not navigated.
75Tell me about the home-screen widgets.
  • 5 Glance widgets; pure tested use cases build the snapshot
  • WidgetSnapshotStore → renders instantly and offline
  • Glance is Compose-shaped but doesn't render Compose
  • Compiles to RemoteViews, inflated by the launcher's process
  • No Canvas, no blur, no animation → charts drawn to bitmaps
And a widget can't read MaterialTheme, so WidgetPalette mirrors the axes.
76How does the Health Connect integration work, and why read-only?
  • Steps + sleep on every app foreground, max once / 15 min
  • Logged against a fitness or sleep goal, created if absent
  • A day is never counted twice; today tops up by the difference
  • Read-only: only READ_STEPS + READ_SLEEP declared
A write permission would contradict what the rationale screen promises on a screen the system itself surfaces.
77Why minSdk 26, targetSdk 35, compileSdk 35?
  • compileSdk — what I compile against
  • targetSdk — the behaviour contract (edge-to-edge, notif permission)
  • minSdk 26 — java.time + notification channels, no desugaring
  • Lower buys a fraction of a percent for a second code path
78What is the difference between the app's debug and release build types here?
  • debug: .debug suffix → both builds on one phone at once
  • release: R8 minify + shrink resources
  • Real key when credentials resolve, else debug key
  • But the upload task refuses without the real key
A debug-signed APK in a tester's hands can never be updated by a properly signed one.

85What is not tested?

  • Live Firebase not exercised — rules run on the emulator by design
  • TalkBack verified by hand
  • Strongest where the logic is: domain/ is near-fully covered

  • LLM cost → cache by prompt, batch the import, per-user quota
  • Wouldn't break: the security model, and offline
Rules are per-document and per-field, not per-query — so they don't care about volume.
94What is the biggest technical risk in this project?
  • A third-party model I don't control, retired on a rolling schedule

  • Second: no server-side cascade — deletion correctness is the client's
