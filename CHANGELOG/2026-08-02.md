## 🐛 Diagnosis
Reported as "the emulator script doesn't open". It did open — `Emulator ready
(9s)`, `[DONE]`, exit 0. The script was never at fault. What failed was rendering:

- `sys.boot_completed=1`, app installed and running, but the **guest**
  framebuffer was entirely black (a 22 KB PNG; a real frame is ~500–700 KB).
  Capturing guest-side is what separated "host window problem" from "GPU
  emulation problem" — both look identical on screen.
- Emulator log: `translator::gles2::glAttachShader:509 error 0x502`
  (`GL_INVALID_OPERATION`) repeatedly, then
  `ERROR | Failed to find EmulatedEglImage:84/85/86`.
- It happened immediately after `Successfully loaded snapshot 'default_boot'`.

Two separate causes, one masking the other:

1. **Snapshot-restored GL state.** `-Recover` (cold boot) restored rendering
   immediately — 22 KB → 550 KB framebuffer. This is the flag added yesterday
   doing exactly its job, and it is now genuinely exercised: the graceful
   `emu kill` did *not* work on the wedged emulator, so the AVD-scoped
   force-stop path ran for real and cleared 2 stale lock entries.
2. **An AVD profile too small for the host and the image.** Surfaced once the
   black screen was gone, as a SystemUI ANR.

## 🔧 AVD hardware tuning
`~/.android/avd/Pixel_10_Pro_XL.avd/config.ini`. Original saved alongside as
`config.ini.bak-before-tuning`.

| Setting | Was | Now | Why |
|---|---|---|---|
| `hw.ramSize` | 2048 | **4096** | 2 GB is below what an API 37 image with Play Services needs; host has 31.6 GB |
| `vm.heapSize` | 256 | **512** | Matches the larger RAM |
| `hw.cpu.ncore` | 4 | **6** | Host is a 12-core / 14-thread Ultra 7 155U |
| `hw.gpu.mode` | `auto` | **`angle_indirect`** | See below |

**`angle_indirect` is chosen for this machine specifically.** The host has no
discrete GPU — only Intel integrated graphics. `auto` resolves to the host
**OpenGL** path, and Intel's Windows OpenGL driver is precisely where the GLES
translator fails (`Failed to find EmulatedEglImage`). `angle_indirect` routes
GLES through **Direct3D 11**, which Intel's Windows drivers handle far better.
If it ever misbehaves, `swiftshader_indirect` is pure software — slower, but it
works everywhere.
