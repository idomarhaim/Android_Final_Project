## ✨ Summary
Diagnosed an emulator that booted to a **black screen** and then to a *"System UI

No app code changed — this is machine-local emulator configuration, recorded here

## 🐛 Diagnosis
Reported as "the emulator script doesn't open". It did open — `Emulator ready
(9s)`, `[DONE]`, exit 0. The script was never at fault. What failed was rendering:

- `sys.boot_completed=1`, app installed and running, but the **guest**
  framebuffer was entirely black (a 22 KB PNG; a real frame is ~500–700 KB).
  Capturing guest-side is what separated "host window problem" from "GPU
  emulation problem" — both look identical on screen.
- Emulator log: `translator::gles2::glAttachShader:509 error 0x502`
  (`GL_INVALID_OPERATION`) repeatedly, then
  `ERROR | Failed to find EmulatedEglImage:84/85/86`.
- It happened immediately after `Successfully loaded snapshot 'default_boot'`.

Two separate causes, one masking the other:

1. **Snapshot-restored GL state.** `-Recover` (cold boot) restored rendering
   immediately — 22 KB → 550 KB framebuffer. This is the flag added yesterday
   doing exactly its job, and it is now genuinely exercised: the graceful
   `emu kill` did *not* work on the wedged emulator, so the AVD-scoped
   force-stop path ran for real and cleared 2 stale lock entries.
2. **An AVD profile too small for the host and the image.** Surfaced once the
   black screen was gone, as a SystemUI ANR.

## 🔧 AVD hardware tuning
`~/.android/avd/Pixel_10_Pro_XL.avd/config.ini`. Original saved alongside as
`config.ini.bak-before-tuning`.

| Setting | Was | Now | Why |
|---|---|---|---|
| `hw.ramSize` | 2048 | **4096** | 2 GB is below what an API 37 image with Play Services needs; host has 31.6 GB |
| `vm.heapSize` | 256 | **512** | Matches the larger RAM |
| `hw.cpu.ncore` | 4 | **6** | Host is a 12-core / 14-thread Ultra 7 155U |
| `hw.gpu.mode` | `auto` | **`angle_indirect`** | See below |

**`angle_indirect` is chosen for this machine specifically.** The host has no
discrete GPU — only Intel integrated graphics. `auto` resolves to the host
**OpenGL** path, and Intel's Windows OpenGL driver is precisely where the GLES
translator fails (`Failed to find EmulatedEglImage`). `angle_indirect` routes
GLES through **Direct3D 11**, which Intel's Windows drivers handle far better.
If it ever misbehaves, `swiftshader_indirect` is pure software — slower, but it
works everywhere.

# Health Connect integration — steps & sleep (session `health`)

> **Branch:** `feat/goalpilot-implementation`

## ✨ Summary
Replaced the `HealthConnectManager` stub with a real, read-only Health Connect
integration (spec §5, §6 nice-to-have). A **Sync health data** card on the
dashboard pulls the last seven days of steps and sleep, proposes which goal each
day should be logged against, and writes nothing until the user confirms — the
same review-before-write policy as the Google Tasks import and smart add.

This closes the first of the two remaining §6 nice-to-haves. Competitive
challenges is now the only one left.

## 🏗️ What was built

**Domain (pure Kotlin, no Android — so the rules are JVM-testable)**
- `domain/model/HealthMetrics.kt` *(new)* — `HealthAvailability`, `DailySteps`,
  `SleepNight`, `SleepInterval`, `HealthSnapshot`, and `toSleepNights()`.
- `domain/repository/HealthRepository.kt` *(new)* — the read-only port.
  `requiredPermissions` is a plain `Set<String>` so `domain/` stays Android-free.
- `domain/usecase/BuildHealthProposalsUseCase.kt` *(new)* — every filing rule:
  which goal a metric lands in, what to propose when none fits, what to skip.

**Data**
- `data/health/HealthConnectManager.kt` — now implements `HealthRepository`.
  Steps come from `aggregateGroupByPeriod` (the provider de-duplicates across
  apps during aggregation, which `readRecords` does not); sleep is read raw
  because attributing a session that crosses midnight is our decision, not the
  aggregator's.

**Two decisions worth recording**

1. **Sleep is filed under the day you woke up.** Sleep crosses midnight, so a
   session has two candidate dates. Waking day is what a person means by "last
   night"; bucketing by start date would file Friday night under Friday and leave
   Saturday looking empty.
2. **Overlapping sleep sessions are merged, not summed.** Health Connect
   aggregates every app on the device. A phone with both a watch app and a sleep
   tracker reports the same night twice — naive summing claims sixteen hours.

## 🔑 `ProgressEntry.sourceKey` — exact dedupe instead of guesswork
Steps are cumulative, so re-syncing a day already logged silently doubles the
week. Added `sourceKey` to `ProgressEntry` / `ProgressDto` (e.g.
`hc:steps:2026-08-01`), so a sync recognises its own earlier writes exactly.

This is the fix the Google Tasks import wanted and could not have: its rows carry
no external id, so it dedupes by title and the backlog says so. Health readings
have a natural identity, so this one does not have to guess. Additive and
nullable — existing progress documents are unaffected.

## ⚙️ Dependency pinned by the toolchain, not by preference
`androidx.health.connect:connect-client` is pinned to **`1.1.0-beta01`**, not the
stable `1.1.0`. Both `1.1.0` and every `1.1.0-rc*` demand **compileSdk 36 AND AGP
8.9.1+**; this project is on compileSdk 35 / AGP 8.7.3 / Gradle 8.10.2, and
`checkDebugAarMetadata` rejects them outright. `beta01` is the newest release that
builds against the current toolchain, and the APIs used here have been settled
since `1.0.0-alpha`.

Note there is **no stable 1.0.0** — that line ends at `1.0.0-alpha11`, so the
stub's original "the client is alpha-only" objection was true when written.
Moving to `1.1.0` means bumping AGP, the Gradle wrapper and compileSdk together;
that is a toolchain change with far wider blast radius than this feature, so it
was deliberately **not** bundled in. Logged under TODO → FUTURE.

## 🔒 Read-only by design
Only `READ_STEPS` and `READ_SLEEP` are declared — no write permission exists, so
the user is never asked for one. `HealthPermissionsRationaleActivity` is required
(Health Connect refuses permissions to an app that cannot explain itself) and is
reachable two ways: `ACTION_SHOW_PERMISSIONS_RATIONALE` for Android 13 and below,
and a `VIEW_PERMISSION_USAGE` `<activity-alias>` for 14+. It has to be an alias —
the system requires `START_VIEW_PERMISSION_USAGE` on the component it launches,
and putting that on the activity itself would also gate the 13-and-below entry
point, which is not allowed to be gated.

## 🎨 Skin canvases re-tinted — the background was reading as grey

Second track today, from the `theming` session. The skins shipped on 2026-07-31
with a tinted `background`/`surface`, but at **chroma 13** (max−min across RGB)
the tint was invisible on a phone: both skins read as plain grey, which defeats
the point of having skins.

**Why it could not just be saturated.** A more saturated canvas is a *darker*
canvas, and every accent painted directly on it loses contrast. The shipped
accents sat **0.05 above the 4.5:1 floor** — `secondary on surface` was at 4.55.
There was no headroom at all; raising canvas chroma by even a few points would
have failed `ThemePaletteTest`.

So the fix was to buy headroom first: both skins' accents moved from Material
tone 40 to ~tone 35, which let the canvases roughly **triple in chroma**.

| | before | after | chroma |
|---|---|---|---|
| Aurora light | `#EAEEF7` | **`#D0E2F5`** sky blue | 13 → **37** |
| Blossom light | `#FCEEF0` | **`#FBDEE4`** blush pink | 14 → **29** |
| Aurora dark | `#111318` | **`#0C1520`** deep navy | 7 → **20** |
| Blossom dark | `#191113` | **`#221014`** deep wine | 8 → **18** |

Accents deepened to match — Aurora `#0A56C4` / `#0A6045` / `#00596B`, Blossom
`#B8215A` / `#A4460E` / `#8A5400` — along with the neutral ladder, `outline` and
`onSurfaceVariant` so the whole scheme carries the hue rather than a tinted page
sitting under grey furniture.

**Hero gradients deliberately unchanged.** They are now brighter than `primary`,
which is the point: the hero card has to pop off a canvas that is itself
coloured.

Iterated with a throwaway contrast checker (scratchpad, not committed) that
mirrors `ThemePaletteTest` for the affected pairs — ~1s per candidate instead of
a 40s Gradle round trip. Three candidate palettes were rejected by it before
these passed.

Also fixed: `gp_window_background` was still `#F9FAFF` from an earlier draft
while the canvas was `#EAEEF7`, so cold start flashed a colour the app never used
again. Both the light and `values-night` values now track the Aurora tokens
exactly, and `colors.xml` says so in a comment.
