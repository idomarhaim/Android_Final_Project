  This mattered because a retired model fails *silently*: the client falls back
  to local tips by design (spec §8), so the AI would have just looked bland

  decommissioned 2026-10-30. Moved `firebase.json` and `functions/package.json`

  `firebase-tools` 15.25.1 globally, so `firebase deploy` is now available.

## 🤖 Dead LLM code → shipped features
- **`classifyTask` had no UI**, so the spec §6 *Bonus* ("automatic classification
  of tasks into goals, including a suggestion to create a new goal") was not
  demonstrable. Added the **"Smart add a task"** card to the dashboard:
  free-text task → `classifyTask` → a confirmation dialog showing the chosen
  goal (or a proposed new one) and the estimated points → the user confirms
  before anything is written. A `suggestedGoalId` that matches no real goal is
  discarded rather than trusted (spec §8: LLM output can be inconsistent).
- **`scoreTask` was never called** from the client at all. Wired it to a ✨
  button on the add-task row in `GoalDetailScreen`, which fills the points field
  — spec §6 Core, "point scoring for tasks". Falls back to a deterministic local
  estimate (`5 + 3×words`, clamped 5..50).

## 🐛 Correctness fixes
- **`addFriend` accepted any string.** A mistyped code wrote a friend edge
  pointing at nobody, permanently invisible everywhere. It now rejects uids with
  no `publicProfiles` document and surfaces the repository's own error text
  instead of a generic "Could not add friend".
- **Friends leaderboard could drop friends.** It fetched the global top-100 by
  points and filtered client-side, so any friend outside that window vanished —
  exactly the friend a new user just added. "Friends" mode now fetches profiles
  **by document id** (`whereIn` on `documentId()`, chunked at Firestore's
  30-value cap). Ranking moved into a pure, unit-tested
  `List<LeaderboardEntry>.rankedByPoints()`.
- **Friend code was the raw 28-character Firebase uid** — copy-pasteable but not
  typeable in a live demo. Added `FriendCode`: a 6-character code over an
  alphabet that omits the ambiguous `I O 0 1`. Allocated on first sign-in
  (uniqueness-checked, back-filled for existing accounts), mirrored onto
  `publicProfiles` for lookup, shown large on the Profile tab, and normalised as
  the user types in the add-friend dialog.
- **Repository flows pinned the wrong account.** Every `observe*` read
  `auth.currentUser` once at Flow-construction time, so signing out and into a
  second account in the same process served the first user's data — precisely
  the spec §7 two-user demo. Added `FirebaseAuth.uidFlow()` and rebuilt the goal,
  task, progress and social flows on top of it with `flatMapLatest`.
- **Doc/code mismatch:** `FirestorePaths.FRIENDS` claimed friends live under
  `publicProfiles/{uid}/friends/`; the code has always used `users/{uid}/friends/`.

**Region choice — `us-central1` everywhere.** Tel Aviv (`me-west1`) was the
obvious pick for latency and *is* supported, but Cloud Storage's always-free 5 GB
applies only to `us-east1`/`us-west1`/`us-central1`, so an Israeli bucket bills
from the first byte. Firestore's free tier has no region restriction; Storage's
does. Latency is a non-issue in practice because Firestore's offline cache is on
by default, so reads are local and writes are optimistic.

**Cost guard** — billing budget with alerts at 50/90/100 % of $1, with all
credit types included so it tracks *net* spend. Deliberately **alerts-only**, not
spend-cap enforcement: a spend cap pauses services until manually lifted (up to
an hour to resume), covers only one project + service, and tracks gross cost
with savings excluded — it would fire while the actual bill is $0 and kill the
demo.

## 🧭 End-to-end run — the whole chain verified on a device
Third track: the app was driven on the `Pixel_10_Pro_XL` emulator (API 37 /
Android 17) against the live `goalpilot-56e30` backend. **Every assertion below
was checked against Firestore, Cloud Storage or the function logs — not read off
the UI**, because this app is designed to degrade silently (spec §8) and a broken
backend looks almost identical to a working one on screen.

| Layer | Evidence |
|---|---|
| Google Sign-In → Firebase Auth | `users/cTmjUK6…` created; `auth: VALID` in function logs |
| Profile bootstrap | `users/` **and** `publicProfiles/` both written, Hebrew display name intact |
| `FriendCode` | `NDXVJC` allocated on first sign-in and mirrored to the public profile |
| Goal create | `Run 10k` · `category=FITNESS` · `colorHex=#0B6E4F` (category→colour mapping correct) |
| **Task completion transaction** | task `done=true` · goal `currentValue 0→1` · user `points 0→10` · publicProfile `points 0→10, level 1` |
| Storage upload | `progress_images/{uid}/{uuid}.jpg`, 147 443 bytes, under the deployed rules |
| Progress entry | `users/{uid}/goals/{goalId}/progress/…` with `value`, `goalId` and a signed `imageUrl` |
| GROQ `getRecommendations` | live tips returned |
| GROQ `scoreTask` | live point estimate returned |

**The transaction is provably atomic.** `task.completedAt` and `goal.updatedAt`
came back as the *same* millisecond (`1785505622675`), which cannot happen with
sequential writes — the four-document update in `TaskRepositoryImpl.setDone`
really does run as one Firestore transaction.

**Both LLM features are provably live, not falling back.** This needed a
deliberate test because `RecommendationRepositoryImpl` swallows every GROQ
failure into a deterministic fallback:
- `getRecommendations` returned *"Start a 5-Minute Daily Habit"*, *"Set Clear
  Goals"*, *"Start Small"*. The fallback can only ever emit *"Start with one
  goal"*, *"Keep the streak alive"* or *"Nudge: {goal}"* — so these came from the
  model.
- `scoreTask` returned **18** for "Run 5km along the beach". The fallback is
  `5 + 3×words`, which for five words is exactly **20**. A different number is
  proof the call reached GROQ.

### 🐛 Found during the run
- **`StorageRepositoryImpl` hardcodes a `.jpg` extension** for every upload
  (`"$folder/$uid/${UUID.randomUUID()}.jpg"`), so a PNG lands in the bucket named
  `.jpg` with `contentType: image/png`. Functionally harmless — Firebase infers
  the type from the bytes — but the extension misreports the content. Not fixed
  yet.
- The app process restarted once mid-run with **no** entry in the crash buffer,
  no `AndroidRuntime` fatal and no kill record; it recovered cleanly to the
  dashboard and never recurred. Most likely emulator memory pressure rather than
  an app defect, but it is recorded here rather than dismissed.

### Notes for repeating this
- UI automation via `adb shell input` works, with two traps: `input text` is
  **ASCII-only** (the app itself handles Hebrew fine — the limitation is the
  tool), and the first tap outside a focused text field is consumed dismissing
  the IME, so action buttons need tapping twice. The emulator's floating IME
  panel also overlaps the left edge and can cover controls; `adb shell ime
  disable` clears it (re-enable afterwards).
- `adb push /sdcard/...` from Git Bash needs `MSYS_NO_PATHCONV=1`, otherwise the
  path is rewritten to `C:/Program Files/Git/sdcard/...`.

## 📥 Google Tasks import — spec §6 nice-to-have, shipped
Fourth track. `data/tasks/GoogleTasksClient.kt` was a compiling stub; it is now a
real, verified feature.

**Deliberately did not follow the stub's own activation plan.** It called for
`google-api-client-android`, `google-api-services-tasks` and
`google-auth-library-oauth2-http` — several megabytes plus a second auth stack,
for what is literally two GET requests against an endpoint we already hold
credentials for. Instead: `GoogleAuthUtil` (already in `play-services-auth`)
mints the access token from the existing Google Sign-In, two
`HttpURLConnection` calls hit the Tasks REST API, and the `kotlinx.serialization`
already on the classpath parses them. **Zero new dependencies.**

- `GoogleAuthClient` now requests `tasks.readonly` at sign-in. Accounts that
  signed in *before* the scope existed throw `UserRecoverableAuthException`;
  `TasksImportResult.NeedsConsent` carries Google's own consent `Intent` up to
  the screen, which launches it and retries on success — no sign-out needed.
- `DashboardViewModel.importGoogleTasks()` fetches open tasks, runs each through
  the same `classifyTask` function the "Smart add" card uses, and opens a review
  sheet. Nothing is written until the user confirms — same policy as smart add.
- Read-only throughout: GoalPilot never writes back to Google Tasks.

### Safeguards
- **Capped at 15 tasks per run** — each costs a `classifyTask` call and GROQ's
  free tier allows 30 requests/minute; an unbounded list would exhaust it and
  half the classifications would silently fall back.
- **Deduped by title** on re-import. Firestore tasks carry no external id, so
  title is the only handle available; storing `externalId` on `Task` would make
  this exact.

### 🐛 Found by testing, fixed
One real Google Tasks entry was a pasted multi-paragraph message. Google Tasks
titles are unbounded, and the review row had no line limit — that single entry
pushed the other eight off the dialog, making them unreachable. Fixed at both
layers: `maxLines = 2` + ellipsis on the review rows, and a 120-character clamp
(cut on a word boundary) in `GoogleTasksClient`, so an oversized title cannot
become a giant task or goal name — or burn tokens on every classify call.

### OAuth prerequisites learned the hard way
`tasks.readonly` is a **sensitive** scope, unlike the `email`/`profile` used by
plain sign-in, and that changes the rules:
- Publishing status must be **Testing**. An unverified app *in production*
  returns `Error 403: access_denied` with **no override**. Testing shows a
  warning the tester can click past.
- The account must be on the **Test users** list. Being the project Owner grants
  nothing here.
- The "Ineligible accounts not added" dialog means the address is **already on
  the list** — it is a duplicate rejection, not a permissions problem.
- The consent screen's app name comes from the OAuth **Branding** page of the
  *Firebase* project, which is easy to confuse with the leftover "My First
  Project". Google appends the project number to unverified app names
  (`GoalPilot-297750736036`) as anti-impersonation; that suffix cannot be
  removed without verification.

## 🎨 Selectable skins + a UI/UX pass

Fifth track, and the first purely visual one. The brief: the app looked bland,
and it should ship two switchable colour skins — a blue/green one as the default
and a pink/orange one. No functional change.

### Why it looked bland — two root causes, not one
1. **`GoalPilotTheme(dynamicColor = true)`.** Material You was on by default, so
   on any Android 12+ device the *wallpaper* picked every colour and the brand
   palette in `Color.kt` was dead code. That is exactly the washed lavender-grey
   in the "before" screenshot. Dynamic colour is now **removed** — it cannot
   coexist with a user-chosen skin, because two colour authorities cannot both
   win.
2. **The palette only defined ~19 of the ~30 Material 3 roles.** Every unset
   token silently fell back to the Material *baseline* (purple-grey), and `Card`
   reads `surfaceContainerHighest` — one of the unset ones. So even with dynamic
   colour off, every card would have been baseline grey.

Also fixed while in there: `md_light_onPrimaryContainer` was
`Color(0xFF00201400)` — ten hex digits, which binds `Color(Long)` and truncates
to `0x00201400`, i.e. **alpha 0**. That token had been fully transparent since it
was written; dynamic colour had been hiding it.

### The two skins
- **Aurora** *(default)* — ocean blue → teal → evergreen.
- **Blossom** — sunset rose → coral → amber.

Each ships a complete light **and** dark `ColorScheme` (all 30 roles, including
the whole `surfaceContainer*` ladder) plus off-Material brand accents
(`GpAccents.heroGradient`, `positive`) reached through `MaterialTheme.gpAccents`.

- `domain/model/AppSkin` is a pure enum — id + display copy, no Compose types,
  the same split `GoalCategory` uses for `iconKey`.
- Persisted device-locally through `AppPreferencesRepository` →
  `SharedPreferences`. Deliberately **not** DataStore and **not** Firestore: the
  theme must be known before the first frame, and a skin is a property of this
  install, not of the account. Exposed as a hot `StateFlow` so composition #1
  already holds the stored value — a cold flow would paint one frame in the
  default skin and visibly repaint.
- `MainActivity` field-injects it, because the skin has to be known *outside*
  `GoalPilotTheme` and every `hiltViewModel()` in this app is created inside it.
- Picked on **Profile → Appearance**, showing the real gradient rather than a
  colour name, applied instantly (no "apply" button — the screen around it is the
  preview), and modelled as a radio group so TalkBack says "selected, 1 of 2".

### Surfaces: the page is the canvas, cards float
Material's filled `Card` uses `surfaceContainerHighest`, which in a light scheme
is *darker* than the page — so a screen of stacked cards reads as grey blocks
with white gutters. Introduced **`GpCard`**, which inverts that: the page is a
tinted tone (`#EAEEF7` Aurora / `#FCEEF0` Blossom) and cards fill with
`surfaceContainerLowest`. Dark mode keeps the normal relationship. All 18 card
call sites moved over; `Card` is now only used inside `GpCard`.

### UI/UX changes (no functionality touched)
- **Dashboard hero** — the points card is now the one branded surface on the
  screen: brand gradient, display-size point count, level pill, rounded progress.
- **Overview card** — `7 goals • 1 tasks done • 1 this week` (one run-on
  sentence) became three labelled metrics; the ring sweeps the brand gradient.
- **`GpLinearProgress`** — a rounded, animated 10dp pill replaces Material's
  4dp square-capped hairline everywhere (hero, level, goal cards, bar chart).
  Keeps `ProgressBarRangeInfo` semantics, so TalkBack is unchanged.
- **Type scale** — negative tracking on headlines/titles, and *every* style the
  app uses is now declared. `headlineSmall` (Profile) was previously falling back
  to the Material baseline, so that screen quietly mixed two type scales.
- **Shapes** — 20dp cards, 12dp fields (was 4dp, which looked boxy inside a card).
- **Bottom bar** — outlined icons when idle, filled when selected, and the bar
  carries the card fill so it reads as chrome, not another band of background.
- **Sign-in** — full brand sweep instead of `primary`→`primaryContainer` (two
  tones of one hue looked like a flat fill with a seam) and a white button, the
  only fill that reads against both skins' gradients.
- **`BrandSystemBars()`** — edge-to-edge meant black status icons on the
  saturated sign-in gradient. A screen can now opt out of the theme's system-bar
  colouring and it reverts on dispose.

### Two real defects the new tests caught
- **`GoalCategory` had three near-identical greens** (Fitness `#0B6E4F`,
  Nutrition `#38A169`, Finance `#2F855A`). Those colours are the analytics
  chart's series colours, so three of ten categories were indistinguishable at
  bar width. Replaced with ten hues spread around the wheel, every one ≥ 4.75:1
  on white (they are used as *text*, not just fills) and ≥ 97 apart in weighted
  RGB. The distinctness test rejected two of my own drafts before this one
  passed. **No Firestore document is rewritten** — `colorHex` is persisted per
  goal, so an untouched goal keeps its old colour (visible on the Goals-tab
  screenshot). New goals get the new defaults, and because
  `AddEditGoalViewModel.save()` re-derives `colorHex` from the category on every
  save, an old goal also picks the new one up the next time it is edited.
- **Goal accents were unreadable in dark mode.** They are hex chosen for a light
  background and then painted as text; `#5145CD` on a dark surface is ~2.8:1.
  `String.toGoalAccent()` now lifts them to a fixed HSL lightness on dark
  surfaces, preserving hue so a goal stays "the purple one".
