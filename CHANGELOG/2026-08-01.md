# Changes — 01/08/2026

> **Branch:** `feat/goalpilot-implementation`

## ✨ Summary
Added a `scripts/` folder of one-click launchers so the entire run loop — bring a
device up, build, install, launch — happens without ever opening the project in
Android Studio. Motivation: day-to-day editing happens in VS Code, and a second
IDE holding a Gradle daemon on the same `app\build\` directory is the one thing
that genuinely collides (Windows file locks), so the fix is to never need it.

## 🚀 New: `scripts/`

- **`run-goalpilot.ps1`** — the real work. Resolves everything from the repo
  rather than the machine: `sdk.dir` from `local.properties`, `JAVA_HOME` from
  `org.gradle.java.home` in `gradle.properties` (the machine default is JDK 25,
  which AGP rejects). Picks a target — physical phone if attached, else a running
  emulator, else boots the AVD — waits for `sys.boot_completed=1`, pins
  `ANDROID_SERIAL`, runs `:app:installDebug`, then `am start`s `MainActivity`.
  Flags: `-Target auto|emulator|device`, `-Avd`, `-SkipInstall`, `-ColdBoot`,
  `-Logcat`, `-BootTimeoutSec`.
- **`Run GoalPilot.cmd` / `Start Emulator Only.cmd` / `Run On Phone.cmd`** —
  double-clickable wrappers. Each keeps its window open so the output is readable.
- **`create-desktop-shortcuts.ps1`** — optional; puts the three `.cmd` files on
  the Desktop as `.lnk` icons. Not run automatically (it writes outside the repo).
- **`scripts/README.md`** — usage, troubleshooting, and why Android Studio is
  avoided.

Design notes worth keeping:

- **`adb devices` state is not proof a device is usable.** adb keeps reporting
  `device` while an emulator shuts down. Every candidate is probed with
  `getprop sys.boot_completed` before selection (`Test-DeviceReady`), which turns
  a confusing Gradle `No connected devices!` into a clear message. The boot loop
  waits for attach **and** readiness, since adb answers long before Android is up.
- **Expected failures exit cleanly** via a `Fail` helper rather than `throw` — a
  PowerShell stack trace in a double-clicked window is noise. Exit code is still
  non-zero.
- **`am start` exits 0 even when it fails.** It prints `Error: Activity class …
  does not exist` and still returns 0, so a bad launch would have been reported
  as success. The output is inspected, not just the exit code.
- **Exit codes must be explicit.** The `-SkipInstall` path originally used
  `return`, which inherits `$LASTEXITCODE` from the last native call — a clean
  run could exit non-zero. Both terminal paths now `exit 0`.
- The wake/`dismiss-keyguard` step is gated to emulators; a real phone's lock
  screen is left alone. It runs when *reusing* an idle emulator too, otherwise
  the app launches behind a black screen.

### Failure hit and resolved during testing
The corrupt-quickboot-snapshot failure mode documented in `scripts/README.md` was
**not** hypothetical — it was triggered for real. Repeatedly hard-killing the
emulator to exercise the boot path corrupted its quickboot snapshot and left
stale `hardware-qemu.ini.lock` and `multiinstance.lock` entries in
`~/.android/avd/Pixel_10_Pro_XL.avd`. After that the emulator would start (qemu
alive) but sit `offline` forever, never reaching `sys.boot_completed`; two runs
died with `InstallException: device offline`. Root cause was the emulator state,
not the script. The documented recovery — stop `qemu-system-x86_64`, delete the
`*.lock` entries, boot with `-ColdBoot` — **was executed and did resolve it**
(ready in 87 s), and the full chain passed immediately afterwards. So the
recovery commands in `scripts/README.md` are exercised, not theoretical.

# Follow-up — the emulator singleton now enforces itself

## ✨ Summary
The launchers above were built by **two sessions at once**, which is precisely the
situation [SESSIONS.md](../SESSIONS.md) exists to prevent. The collision was real:
neither session claimed `scripts/`, both edited the same files, one session
deleted the other's changelog section (restored before the commit), and — the
part that caused actual damage — both drove `Pixel_10_Pro_XL`. One session's
`adb emu kill` during the other's build is the most plausible cause of the
corrupt quickboot snapshot and the two `InstallException: device offline` runs
recorded above.

The board declared the emulator exclusive but nothing enforced it. Now the tool
does.

## 🔒 Cross-session device claim
`run-goalpilot.ps1` takes an exclusive claim on its target for the duration of a
run. A second session is refused, and told who holds it:

```
ERROR: 'avd-Pixel_10_Pro_XL' is already being driven by another session.
ERROR:   PID 22816 (namei) since 2026-08-01 20:32:29
ERROR:   repo: C:\Dev\Android_Final_Project
```

Design decisions worth keeping:

- **Keyed on the AVD name, not the serial.** Emulator ports are recycled, so
  `emulator-5554` is not a stable identity; `adb emu avd name` is. Physical
  devices key on their serial.
- **An exclusive OS file handle, not a PID file.** Windows drops the handle when
  the process dies, so a crashed or killed run *cannot* leave a stale claim —
  the failure mode the board itself warns about ("a stale claim blocks work
  nobody is doing"). Nothing to clean up by hand, ever. Verified by test.
- **Held only for the run.** Released before the `-Logcat` tail (read-only, can
  run for hours) and on the `-SkipInstall` exit, so a booted emulator is left
  unowned and reusable.
- Claimed *before* booting or recovering, so nothing destructive is ever done
  outside the claim.

## 🩹 `-Recover`, scoped to one AVD
Replaces the blanket `Get-Process qemu-system-x86_64* | Stop-Process` that
`scripts/README.md` used to recommend — which kills *every* emulator on the
machine, including other sessions'. `-Recover` asks the AVD to shut down
gracefully, force-stops only processes whose command line names **that** AVD,
clears only **that** AVD's `*.lock` entries, then cold-boots.
